## 0. 먼저 — 기준선을 다시 떠야 했다

인계 문서의 숫자는 그대로 쓸 수 없다. **코퍼스가 움직였다.** 09-10 20:51에
인덱스가 다시 쓰였고 qa는 247 → 254(이 레포), 2,003(1차)로 늘었다. 오늘 새로
얼린 스냅샷의 기준선은 이렇다.

| | 인계 문서 | **오늘 기준선** |
|---|---|---|
| Set A found / **top3** / MRR | 0.75 / **0.70** / 0.571 | 0.75 / **0.70** / 0.565 |
| Set B found / top3 | 0.05(top3) | **0.12** / 0.05 |
| 코드축 top5 / recall@10 / memory@3 | 0.92 / 0.77 / 0.16 | **0.88** / 0.77 / 0.16 |
| 밀어냄 정밀도 (1차) | 9/9 = 100% | **7/10 = 70%** [0.40, 0.89] |
| 밀어냄 정밀도 (2차) | 3/6 = 50% | **4/6 = 67%** |

**코드축 0.92 → 0.88은 이 세션의 변경 때문이 아니다** — 손대기 전에 이미 0.88이었고
3회 반복 모두 0.88이다. 코퍼스가 움직인 결과다.

**1차의 100%는 같은 코퍼스의 새 표본에서도 재현되지 않았다.** 시드가 같아도 코퍼스가
커지면 표본이 바뀌고, 09-10에 라벨한 21건은 이번 표본에 **한 건도** 걸리지 않았다.
새로 뜬 10건을 같은 기준으로 판정해 라벨을 32건으로 늘렸다(심사 §10-3 항목).

> **주의사항 (신규)**: 라벨은 chunk_id로 키를 잡지만 **표본은 코퍼스 크기에 따라 바뀐다.**
> "라벨 0/10"은 라벨이 틀린 게 아니라 겹치지 않은 것이다. 비교 전에 `displacements labelled`
> 줄을 먼저 볼 것.

## 1. 채택 — 통합 노트는 자기 원본의 슬롯을 빼앗지 못한다

### 무엇이 문제였나

스플라이스는 슬롯이 꽉 차면 낡은 히트를 **치환**한다. 후계자가 통합 노트일 때
이건 삭제다. 노트는 **손실 있는 종합**이라서, 종합이 버린 것은 그대로 사라진다.

대표 사례(2차 코퍼스, 실측): 어떤 노트가 그 세션의 비용 결론은 종합했지만
그 세션이 열거한 미커밋 파일 목록을 버렸다. 프로브는 **그 목록**을 찾고 있었다.
질문 겹침 1.00 · 대칭 겹침 1.00 · 답변 겹침 0.63 — **색인 시점 바를 전부 만점으로
통과한다.** 주제로는 정말 같은 것이기 때문이다.

### 무엇을 했나

`orchestrator._splice_superseding`의 **파괴적 분기에서만**, 후계자가 통합 노트이고
밀려날 레코드가 **자기 답변 발췌를 소유**하면 치환을 거부한다. 거부해도 노트는
여유 슬롯이 있으면 여전히 삽입되고, 낡은 쪽에는 superseded 마크가 붙는다.

**"소유"로 좁힌 이유가 핵심이다.** 치환이 파괴할 수 있는 것은 그 레코드가 가진
것뿐이다. 한 턴은 레코드를 둘 남긴다 — 질문이 도착할 때 쓰는 **선주입 로그**와
답이 나올 때 쓰는 **답변 로그**. 선주입 로그는 자기 답이 없고 `## Top results`
인용 덤프만 있으므로, 그 자리를 노트에 내주면 잃는 게 없다. 그게 설계된 노출
경로이고, 1차 코퍼스 라벨도 그것을 legitimate이라 부른다.

처음엔 노트 후계자를 **전부** 막았고, 그게 Set A의 C9를 깼다(0.70 → 0.65).
C9의 정답이 정확히 그 경로였다.

### 측정

| | 기준선 | **채택 후** |
|---|---|---|
| Set A found / top3 / MRR | 0.75 / 0.70 / 0.565 | **0.75 / 0.70 / 0.565** |
| Set B found / top3 | 0.12 / 0.05 | **0.12 / 0.05** |
| 코드축 top5 / recall@10 / memory@3 | 0.88 / 0.77 / 0.16 | **0.88 / 0.77 / 0.16** |
| supersession 재현율 손실 (라벨 기준) | — | **32%** · 맵이 한 바이트도 안 바뀌므로 정의상 무변동 (1회 측정) |
| 2차 코퍼스 밀어냄 | 8/120 · damage **2** | 3/120 · damage **1** |
| 1차 코퍼스 밀어냄 | 10/120 · damage 3 | 10/120 · damage 3 (노트 후계자 없음 → 가드가 아예 안 걸린다) |

파괴 축은 **같은 스냅샷에서 가드만 켰다 껐다** 하며 잰 A/B다 — 재임베딩 실험으로
벡터가 미세하게 드리프트했기 때문에, 오전에 잰 기준선과 나란히 놓지 않고 같은
조건에서 다시 대조했다.

2차 코퍼스에서 사라진 밀어냄 4건 중 **1건이 damage(대표 사례), 3건이 legitimate**이다.
사라진 legitimate 3건은 **정보 손실이 아니다** — 원본이 자리를 지키고, 여유가 있으면
노트도 삽입된다. 바뀐 것은 슬롯이 꽉 찼을 때 둘 중 누가 남느냐다.

> **주의사항 (신규)**: 밀어냄 **정밀도(비율)** 로 이 변경을 읽지 말 것. 분모가 같이
> 줄어 67% → 50%로 "나빠져" 보인다. 모집단이 다르다(심사 지적 #4). 읽어야 할 것은
> **120 프로브당 damage 절대 건수**와 외부 축 4종이다.

## 2. 측정하고 기각 — 출처(provenance) 게이트

노트는 `sources:`에 자기가 만들어진 레코드를 적는다. "노트는 자기가 만들어진
레코드만 대체할 수 있다"는 규칙은 임계값이 아니라 **사실 조회**라서 매력적이었다.

**실측**: 후계자가 노트인 매핑 중 **출처 근거가 없는 것이 43%** (1차 13/30, 2차 5/12).
적용하면 엣지 4건이 지워지고 14건이 노트가 아닌 실제 턴으로 재조준되며,
**새로 생기는 엣지는 0건**(단조성 유지).

**그런데 Set A top3가 0.70 → 0.65로 떨어졌다.** 반례가 분명하다 —
**한 턴이 레코드를 둘 남기는데 노트는 그중 하나만 `sources:`에 적는다.**
C9의 정답 경로가 바로 나머지 하나였다. 레코드 단위로 보면 "출처 없음"이고
턴 단위로 보면 정확하다.

**그래서 43%는 결함률이 아니라 입도 오류다.** 단위는 턴인데 qa 레코드에 턴 id가 없다.
턴 id를 주면 이 게이트는 한 줄 필터가 된다. 그때까지는 실제 답을 거절한다.

파서(`_record_key`, `_consolidation_sources`)는 테스트로 고정해 남겨 뒀다 —
`supersession.py`의 미적용 규칙 주석 관례를 따른다.

## 3. 계측기 수정 — 감사가 자기 신호를 망치고 있었다

`displacement_audit.py`가 "후계자가 잃은 질의 어휘"를 셀 때 밀려난 레코드의
`## Top results` 인용 덤프까지 읽었다. 그 덤프는 **다른 청크의 인용**이고 각각
따로 검색되므로, 거기서 어휘가 빠지는 건 아무것도 파괴하지 않는다.

두 코퍼스에서 suspected damage로 찍힌 것 중 **5건이 선주입 로그의 덤프 어휘**였고
전부 손으로 legitimate 판정이 났다. 이제 **레코드가 소유한 텍스트**(자기 질문 +
자기 답변 발췌)에서만 센다.

| 휴리스틱 | 이전 | **이후** |
|---|---|---|
| 정밀도(두 코퍼스 합) | 3/7 = 43% | **2/3 = 67%** |
| 재현율 | — | 1차 1/3, 2차 1/1 |

재현율이 낮은 것은 구조적이다 — **후계자가 다른 질문에 답하지만 어휘는 안 잃는**
damage는 이 휴리스틱에 원리적으로 안 보인다. 라벨 없이 쓰는 탐지기가 아니라
**라벨할 후보를 좁히는 도구**로 읽을 것.

## 4. 트랙 2의 선결 질문 — 닫혔다. 회귀가 아니다

인계 문서는 "Set B 0.15 → 0.02는 설명되지 않은 하락"이라며 벡터 작업 전에
①골드셋 변경 ②코퍼스 이동 ③회귀 중 무엇인지 가리라고 했다.

**셋 다 아니다. 지표를 맞비교한 것이다.** `docs/plans/2026-09-08-claim-level-retrieval.md`
§8 기준선 표는 이렇다:

| | 09-08 기준선 | **오늘** |
|---|---|---|
| Set B answer_found | 0.15 [0.07, 0.28] | 0.12 [0.05, 0.26] |
| Set B answer_in_top3 | **0.02** [0.00, 0.13] | **0.05** [0.01, 0.16] |

0.15는 **found**, 0.02는 **top3**다. found는 41문항 중 1문항 차이(CI 거의 완전
중첩), top3는 오히려 올랐다. 같은 계획서 본문에도 "Set B 0.12/0.02로 기준선과 같다"가
이미 적혀 있다.

**결론**: 회귀 없음. 트랙 2는 문장 단위 벡터로 바로 가면 된다. 목표는 **found ≥ 0.15 회복**,
top3는 0.05가 기준선.

## 5. 이 세션이 새로 알아낸 구조 — 다음 트랙 1의 근거

### (a) Set A는 노트 회수를 재는 골드셋이다

골드셋 자신의 `note` 필드에 적혀 있다 — 각 질문은 **통합 노트 프론트매터 `query:`의
패러프레이즈**이고 각 구절은 **노트 자신의 표현**이다. 즉 Set A = "통합 노트가 top3에
드는가".

### (b) 스플라이스의 Set A 기여는 정확히 한 문항이다

맵을 통째로 비우고 Set A를 돌리면 **0.70 / 0.65**. 맵을 켜면 0.75 / 0.70.
**supersession 맵이 Set A에 기여하는 것은 C9 하나뿐**이다. 나머지 노트는 스스로
올라온다. (맵의 본업은 정정이고 Set A는 정정을 재지 않는다 — 이 숫자는 맵의 가치가
아니라 **노출 경로로서의 기여**를 말한다.)

### (c) 못 찾는 노트들은 후보 집합에조차 없다 — 그리고 이유가 명확하다

Set A 실패 6문항의 정답 노트를 레인별로 재면:

| 문항 | BM25 순위 | 벡터 순위 | 최종 |
|---|---|---|---|
| C18 | **3** | 236 | 없음 |
| C11 | 91 | 300+ | 없음 |
| C7 | 103 | 132 | 없음 |
| C20 | 143 | 232 | 없음 |
| C5 | 300+ | 300+ | 없음 |
| C10 | 300+ | 9 | 7위 |

**C18은 2,000건 코퍼스에서 BM25 3위인데 최종 50위 안에 없다.** 한국어 자연어 질의의
`effective_bm25_weight`가 0.15라 BM25 3위의 RRF 기여가 벡터 200위대와 비슷해진다.

그리고 **벡터가 노트를 못 찾는 이유가 실물로 확인됐다.** 981자짜리 노트의 임베딩
입력 앞 ~300자가 전부 메타데이터다 — 해시 파일명, **다른 턴에서 복사해 온 질문**,
타임스탬프, `sources_hash`, 해시 파일명 4줄. 노트가 스스로 선언한 제목(본문 H1)은
그 아래 묻힌다. 그런데 **그 H1이 골드 질문을 거의 그대로 다시 말한다.**

### (d) 그래서 노트를 재생성할 필요가 없다

트랙 1 (A)안은 "노트에 자기 질문을 만들어 준다 · 기존 37건 소급 필요"였다.
**이미 있다.** `finalize`가 에이전트 본문을 그대로 싣고, 그 본문은 H1으로 시작한다.

그래서 **읽는 쪽을 고치는** 실험을 했다: qa 청크의 임베딩 입력이 노트면 본문 H1으로
**시작**하고, 출처·텔레메트리 줄을 임베딩 텍스트에서만 뺀다(`content`는 그대로라
BM25·표시·답변 파싱은 무변경). 아래 §"실험 1·2"가 그 결과다 — **두 번 다 기각됐고,
그 과정에서 이 절의 전제가 반증된다.** 노트의 임베딩 정체성은 이 골드셋의 병목이
아니었다. 남는 것은 진단 (c)이고, 그쪽이 다음 작업이다.

기록으로 남길 것: `reflector.py`의 노트 작성 지시문에 "본문은 결론을 말하는 H1으로
연다"를 명시했다. 지금도 노트는 전부 그렇게 쓰이고 있고, 검색 이득은 측정되지
않았으므로 **그 문장은 관행을 적어 둔 것이지 회수 근거가 아니다.**

### 사전 등록 — 재임베딩 결과를 보기 전에 적었다

심사 §1이 "특징을 라벨 보기 전에 고정하라"고 했다. 임베딩 입력 변경의 판정 기준을
**측정 전에** 못 박는다.

- **기대**: Set A top3가 오른다. 실패 6문항 중 5문항의 정답 노트가 H1으로 골드 질문을
  거의 그대로 다시 말하는데, 임베딩은 무관한 메타데이터로 시작하기 때문이다.
- **반드시 무변동일 것**: **코드축**. 코드 청크의 임베딩 입력은 한 글자도 안 건드렸다.
  **코드축이 움직이면 그건 개선이 아니라 버그다.**
- **하한**: Set B found ≥ 0.12 · top3 ≥ 0.05 · Set A top3 ≥ 0.70 · 밀어냄 damage 무악화.
- **채택 규칙**: 하한을 다 지키고 Set A top3가 오르면 채택. **오르지 않으면**
  "측정된 비용(재임베딩)이 있고 측정된 이득이 없다"이므로 주의사항 #8에 따라
  **싣지 않고 그 사실을 적는다.**

### 실험 1 — qa 코퍼스 **전체**의 임베딩 입력을 바꿨다. 기각.

2,003건을 재임베딩했다(로컬 ollama, 25분, ₩0, 오류 0). 사전 등록한 규칙대로 읽는다.

| | 기준선 | 전체 재작성 | 판정 |
|---|---|---|---|
| Set A found / **top3** | 0.75 / **0.70** | 0.65 / **0.65** | ✗ 게이트 |
| Set A MRR | 0.565 | 0.575 | (게이트 아님) |
| Set B found / **top3** | 0.12 / **0.05** | 0.12 / **0.02** | ✗ 하한 |
| 코드축 top5 / recall@10 / memory@3 | 0.88 / 0.77 / 0.16 | **0.88 / 0.77 / 0.16** | ✓ 예측대로 무변동 |

**기각.** 사전 등록 규칙에 따라 싣지 않는다. 스프레드는 세 축 모두 0.00이라
측정 오염이 아니다.

**문항별로 보면 갈린다** — 4문항이 오르고(C10 7→2, C9 3→1, C15 2→1, C19 2→1)
3문항이 떨어졌다(C3 3→없음, C6 1→없음, C4 1→2).

떨어진 쪽의 원인 가설을 하나 세웠다가 **코퍼스로 기각했다**: "Set A 질문이 노트의
복사된 `query:`의 패러프레이즈라서 그 텍스트를 강등하면 골드셋이 구조적으로 벌을 준다."
아니다 — C3·C6의 H1은 골드 질문에 **복사된 질문보다 더 잘 맞는데도** 떨어졌다.

남는 설명은 **경쟁**이다. 이 실험은 노트 20건만이 아니라 **턴 로그 1,983건도 같이**
움직였다. 턴 로그의 임베딩도 해시 파일명 대신 자기 질문으로 시작하게 됐으니
메모리 레인 안의 순위 경쟁이 통째로 재편된다. **결함이 있는 것은 노트 20건인데
나머지 1,983건이 같이 이사한 값을 치렀다.**

> **주의사항 (신규)**: 임베딩 입력 변경은 **레인 전체의 상대 순위**를 바꾼다. 고칠
> 대상이 코퍼스의 1%면 1%만 건드릴 것. 레코드 단위로 옳은 변경이 코퍼스 단위로
> 지는 것은 회수 품질이 아니라 경쟁 구조 때문이다.

### 실험 2 — **노트 20건만** 바꿨다. 이것도 기각. 그래서 결론이 뒤집힌다

실험 1의 남은 설명은 "경쟁"이었다. 그러면 결함이 있는 노트 20건만 바꾸면 이득이
남아야 한다. 턴 로그 1,983건을 원래 형식으로 되돌려 재임베딩하고 다시 쟀다.

| | 기준선 | 실험 1 (전체) | **실험 2 (노트만)** |
|---|---|---|---|
| Set A found | 0.75 | 0.65 | **0.70** |
| Set A **top3** | **0.70** | 0.65 | **0.65** ✗ |
| Set A MRR | 0.565 | 0.575 | **0.507** |
| Set B found / top3 | 0.12 / 0.05 | 0.12 / 0.02 | **0.12 / 0.05** ✓ |
| 코드축 top5 / recall@10 / memory@3 | 0.88 / 0.77 / 0.16 | 무변동 | **무변동** ✓ |

**기각.** 하한(Set B·코드축)은 지켰지만 1차 지표를 못 지켰고, MRR은 더 나빠졌다.

**그리고 문항별로 보면 "경쟁" 가설도 틀렸다.**

| | 기준선 | 실험 1 | 실험 2 |
|---|---|---|---|
| C10 cue-yield-kc | 7 | **2** | 7 |
| C9 bulk-review-split | 3 | **1** | 3 |
| C15 · C19 | 2 · 2 | 1 · 1 | **1 · 1** |
| C4 merge-deploy-order | 1 | 2 | **3** |
| C8 review-rhythm | 1 | 1 | **2** |
| C6 dev-server | 1 | 없음 | **없음** |

실험 1의 큰 개선(C10 7→2, C9 3→1)은 **노트가 아니라 턴 로그 쪽에서 나왔다** —
노트만 바꾸면 둘 다 원위치다. 노트의 정직한 제목이 산 것은 C15·C19 두 문항의
2→1뿐이고, C6 하나를 통째로 잃는다.

**그래서 트랙 1 (A)의 회수 전제는 반증됐다.** "노트에 자기 질문을 주면 검색이
나아진다"는 이 골드셋에서 성립하지 않는다. 못 찾는 다섯 문항(C5·C7·C11·C18·C20)은
**두 실험 어느 쪽에서도 움직이지 않았다.** 임베딩 정체성이 그들의 병목이 아니다.

**병목은 다른 데 있고, 진단이 그것을 가리킨다** (§5-(c)): C18의 정답 노트는
2,000건 코퍼스에서 **BM25 3위**인데 최종 결과 50위 안에 없다. 한국어 자연어 질의의
`effective_bm25_weight`가 0.15라 BM25 3위의 RRF 기여(0.15/63)가 벡터 200위대와
비슷해진다. 그리고 메모리 헤드는 3칸이고 **관련도가 아니라 (타입 우선순위, 그룹
최고점)으로** 뽑힌다 — `orchestrator._merge_memory_results`가 그렇게 적어 두고 있다.

> **주의사항 (신규)**: 임베딩 입력 변경은 **레인 전체의 상대 순위**를 바꾼다.
> 그런데 이번엔 1%만 바꿔도 졌다. 두 실험을 합치면 남는 교훈은 하나다 —
> **이 골드셋의 실패는 회수 표현의 문제가 아니라 융합·슬롯의 문제다.**
> 재임베딩이 필요한 가설은 그 두 개를 먼저 배제한 다음에 세울 것(1회 25분).

## 6. 트랙 3 (LongMemEval 좁은 슬라이스) — 접는다. 이유는 점수가 아니라 구조다

인계 문서의 착수 조건은 "어댑터가 30분 안에 안 되면 접는다"였다. **어댑터 자체는 쉽다.**
스키마를 확인했다:

```
{question_id, question_type, question, answer, question_date,
 haystack_session_ids[], haystack_dates[], haystack_sessions[][{role, content}],
 answer_session_ids[]}            # 턴 단위로는 has_answer: true
```

user→assistant 한 쌍을 qa 레코드 하나로 옮기면 된다 — `query:`=user,
`timestamp:`=haystack_dates[i], `## Answer excerpt`=assistant. 골드는 `has_answer` 턴.

**막히는 것은 코퍼스 구조다.** LongMemEval은 **문항마다 자기 haystack**을 갖는다
(문항당 세션 ~50개). 우리는 **프로젝트당 인덱스 하나**다. 그래서 선택지가 둘뿐인데
둘 다 비교 가능성을 깬다:

1. **문항마다 프로젝트 하나** — knowledge-update 서브셋만 해도 수십 개 × 500턴 임베딩.
   로컬 ollama 실측 기준 1.2 레코드/초 → **문항당 ~7분, 전체 8시간**. 요금은 0원이지만
   맥미니를 그만큼 점유한다.
2. **haystack 전부를 한 코퍼스로 합치기** — 원 벤치보다 훨씬 어려운 과제가 되므로
   논문 수치와 **비교 불가**. 비교 가능성이 목적이었는데 그게 사라진다.

**결론**: 선행 결정("일반 메모리 벤치 점수 경쟁을 하지 않는다")이 옳았다는 쪽에
근거가 하나 더 붙었다 — 우리 인덱스 단위가 프로젝트라서다. 되살리려면
**문항 단위 인덱스를 싸게 만들 방법**(BM25-only 파일럿 등)이 먼저 있어야 하고,
그때도 재는 것은 우리 하이브리드가 아니라 그 축소판임을 명시해야 한다.

## 7. 외부 심사 (DeepSeek `deepseek-reasoner`, 2026-09-11)

설계안 셋을 적대적으로 심사받았다. **판정을 대부분 수용했고, 한 반례가 설계를 바꿨다.**

| 지적 | 처리 |
|---|---|
| "질의가 매치한 어휘를 후계자가 잃으면 거부"는 **순환** — 가드 신호와 damage 라벨의 원인이 같은 계측기다 | **수용.** 그 안을 버렸다 |
| 그 안의 **반례**: 옛 답 "v1 사용" → 새 답 "v1 폐기, v2". 질의에 v1이 있으면 가드가 **정정을 막고 폐기된 답을 보여준다** — damage보다 나쁜 stale 버그 | **수용, 결정적.** 채택안은 "노트 후계자 + 소유한 답"으로만 좁혔다 — 정정 경로(턴→턴)는 손대지 않는다 |
| 억제를 전역으로 끄지 마라 (arXiv 2606.01435는 정책 *제거*가 아니라 *분리*를 말한다) | **수용.** 파괴적 분기에만 적용 |
| 합성 노트는 `supersedes`가 아니라 `derived_from` 관계여야 한다 | **수용.** 채택안이 정확히 그 구현이다 |
| 구조 A(저정보 어휘 2개로 매칭)는 질의 시점 가드로 못 막는다 — 색인 시점 엣지 타입이 필요하다 | **수용, 미해결.** 남은 damage 3건(1차)·1건(2차)이 전부 이 구조다 |
| 비율(정밀도)로 판정하지 마라, 모집단이 바뀐다 | **수용.** 절대 damage 건수 + 외부 축 4종으로 보고한다 |
| n=1 라벨러, IAA 없음 | **부분 수용.** 라벨을 32건으로 넓히고 기존 판정례를 기준으로 삼았다. 블라인드 라벨링·제2 판정은 **안 했다** |

**관련 연구** (겹치는 축을 정직하게 적어 둔다): [Supersede](https://arxiv.org/abs/2606.27472)는
메모리 업데이트 격차를 진단·학습 신호로 만든다. [STALE](https://arxiv.org/abs/2605.06527)은
"낡은 줄 아는 것"과 "바뀐 믿음을 쓰는 것"이 다르다고 한다(최고 모델 55.2%).
[2606.01435](https://arxiv.org/abs/2606.01435)는 증거 추출과 정책 실행의 분리를 주장한다.
**공통점: 전부 "최신 사실을 썼는가"를 잰다.** "억제가 아직 유효한 기억을 지웠는가"를
재는 곳은 못 찾았다 — 밀어냄 감사가 그 자리에 있다.

## 9. 측정 규약 — 달라진 것만

라벨 파일이 하나 늘었고 하나 커졌다. **둘 다 레포 밖**이다(실제 발화를 인용한다).

```
~/.hybrid-search/benchmarks/valuein_displacement_labels.json   v5 · 32건 (기존 22 + 신규 10)

~/.hybrid-search/benchmarks/valuein_cut_labels.json            (변경 없음)
```

두 코퍼스를 함께 재는 형태:

```bash
SNAP=<스냅샷>   # 규약대로 rsync
python benchmarks/recompute_supersession.py --config $SNAP/config.toml
G=~/.hybrid-search/benchmarks
for P in hybrid-search-mcp valuein_homepage; do
  case $P in hybrid-search-mcp) L=$G/hsmcp_displacement_labels.json;;
             *) L=$G/valuein_displacement_labels.json;; esac
  python benchmarks/displacement_audit.py --config $SNAP/config.toml \
    --project $P --sample 120 --labels $L --out /tmp/disp_$P.json
done
```

**임베딩 입력을 바꾸면 재임베딩이 필요하다** (이번엔 기각됐지만 다음에 또 이 길로
올 사람을 위해 비용을 적어 둔다). 벡터 재사용은 `embedding_input`의
sha256로 키를 잡으므로(`index/pipeline._VectorReuse`), 전체 재빌드를 돌리면
**qa 청크만** 새로 임베딩되고 코드·문서는 전부 재사용된다. 실측 비용:
**1.2 레코드/초** (로컬 ollama, ₩0) — qa 2,000건이면 약 28분. 델타 인덱싱은
변경된 qa 파일만 새 형식이 되므로, 기존 코퍼스 전체에 반영하려면 재빌드가 맞다.

행이 하나 더 붙으니 비율이 내려간다 — 카드가 빠진 게 아니다(memory@3 0.16, top5 0.88,
recall@10 0.77 전부 유지). 답 품질 지표는 안 움직였고 구성비만 움직였다.

### F8을 두 번 더 고쳤다 — 슬롯이 자기가 우회하려던 순위로 후보를 골랐다

F8을 넣고도 C18·C20은 안 들어왔다. 계측해 보니 두 결함이 더 있었다.

**(1) 후보 풀이 융합 상위 100개였다.** 슬롯이 존재하는 이유가 "융합이 실격시킨
레코드를 건지는 것"인데, 후보를 바로 그 융합 순서에서 골랐다. C18의 정답은 레인
BM25 **#1**인데 융합 **#51**(실제 가중치 0.15 기준)이고, 실제 파이프라인의 더 깊은
레인에서는 상위 100 밖으로 밀린다. 그래서 슬롯이 계속 BM25 #3을 집었다.
→ 풀에 **어휘 레인 자신의 상위 몇 개**를 더한다(`_LEXICAL_TAIL_POOL = 3`).

> **주의사항 (신규)**: 어떤 순위를 우회하려고 만든 단계는 **그 순위로 후보를 고르면
> 안 된다.** 이건 조용히 실패한다 — 슬롯은 정상 동작하고, 엉뚱한 것을 집을 뿐이다.

**(2) 슬롯이 하나라 문항끼리 빼앗았다.** 풀을 고치자 C18이 들어오고 **C7이 나갔다**
(7 → 없음). 이 레인이 존재하는 이유인 세 문항에서 정답의 레인 BM25 순위는
**#1 한 번, #2 두 번**이고(한 번은 커밋 청크 뒤), 한 자리로는 서로를 밀어낸다.
→ **두 자리**(`_LEXICAL_TAIL_SLOTS = 2`). 코드 꼬리에서 한 칸 더 가져온다.

### 최종 — 채택

| | 기준선 | **채택 후** |
|---|---|---|
| Set A **found** | 0.75 | **0.90** (15/20 → 18/20) |
| Set A **top3** | **0.70** | **0.70** (유지) |
| Set A MRR | 0.565 | **0.600** |
| Set B found / top3 | 0.12 / 0.05 | **0.15** / 0.05 |
| 코드축 top5 / recall@10 / memory@3 | 0.88 / 0.77 / 0.16 | **무변동** |
| 2차 코퍼스 밀어냄 · damage | 8 · 2 | **3 · 0** |
| 1차 코퍼스 밀어냄 · damage | 10 · 3 | 11 · 3 |
| 자기회수 (2차 / 1차) | 105 / 118 | **106 / 119** |

남는 Set A 미회수는 **C5·C11 둘**이다. 둘 다 정답이 레인 BM25 #287·#20이고 벡터에도
안 잡힌다 — 노출이 아니라 **회수** 문제이고, 이 레인의 다음 숙제다.

**"2"라는 숫자에 대해 정직하게**: 한 자리가 스스로 충돌하는 것을 실측으로 봤고
(C18 들어오면 C7 나감) 두 자리가 그것을 푼다. 세 자리는 **시도하지 않았다** —
골드셋에서 파라미터를 쓸어 담는 것이 되기 때문이다. 근거는 "정답이 #2에도 온다"는
구조이지 최적값 탐색이 아니다.

### 문헌 대조 — 우리가 맞게 가고 있나

- [Bruch et al., *An Analysis of Fusion Functions for Hybrid Retrieval*](https://dl.acm.org/doi/10.1145/3596512) (TOIS 2023):
  정규화 점수의 **볼록 결합이 RRF보다 낫고, RRF는 파라미터에 민감하며 "성능이
  비평활(non-smooth)"** 하다. 우리가 만난 벽이 정확히 그 비평활성이다 — 가중치
  0.15가 기울기가 아니라 지배 관계를 만들었다.
- [vstash](https://arxiv.org/abs/2604.15484) (2026): RRF에 **질의별 적응 IDF 가중치**를
  얹어 BEIR 5종 전부에서 NDCG@10 개선. 그리고 **질의의 74.5%에서 두 레인의 top-10이
  불일치**한다고 보고한다 — 고정 가중치 하나가 틀린 도구라는 뜻이고, 우리 관측과 같다.
- [MEMTIER](https://arxiv.org/abs/2605.03675) (2026): 다섯 신호 가중 검색 + PPO로
  가중치를 **학습**한다. 우리 규모에선 과하다.
- [SGMem](https://arxiv.org/html/2509.21212v1): 같은 계열 처방(문장으로 찾아 부모 반환)이
  LongMemEval에서 **+1.4pt**. 이 축의 이득이 원래 작다는 기준점.

**대조 결과**: 방향은 맞다. 다만 **문헌의 처방(적응 가중치·학습 가중치)은 우리가
아직 안 했다.** 오늘 한 것은 그보다 한 단계 아래 — 고정 가중치를 유지한 채 **슬롯
구조로 우회**했다. 질의별 적응 가중치가 다음 후보이고, 오늘의 F6/F7b 실패가 그
근거다(전역 가중치 이동은 교환일 뿐이었다).

## 11. 남은 damage는 어휘로 안 가려진다 — 측정하고 접었다

심사가 권한 "저정보 어휘 배제 / 고유 엔티티 요구"를 코퍼스 문서빈도로 검증했다
(주의사항 #10: 목록을 만지기 전에 DF부터). 1차 코퍼스 질문 1,915건 기준,
라벨된 엣지의 **공유 질문 토큰**과 그 DF는 이렇게 겹친다:

| 판정 | 공유 토큰 (DF%) |
|---|---|
| **damage** | 그림(4.1) 문항(3.8) |
| **damage** | 이제(5.7) 다음(3.7) |
| **damage** | 직접(4.2) 개발(1.1) 명령(0.8) |
| legitimate | 메인(3.7) 머지(3.2) 워크(3.1) |
| legitimate | 메인(3.7) 푸시(2.3) |
| legitimate | 개념(5.1) kc(4.8) |
| legitimate | 브랜(2.3) 따로(2.0) |
| legitimate | 계속(5.1) 다음(3.7) 않아(0.6) |

**두 부류가 같은 구간에 있다.** "DF 2% 미만 토큰을 최소 하나 공유할 것"이라는 규칙을
적용하면 damage 3건 중 2건을 막고 **legitimate 6건을 잃는다.** 공유 토큰 수도
안 가린다 — damage는 2·2·3개인데 legitimate도 2·2·2·3·3개다.

**그래서 이 라인이 임계값에서 네 번 진 이유가 특징 공간에 있다.** 다섯 번째를
시도하지 말 것. 남은 damage를 가르려면 **어휘 밖의 신호**가 필요하다 —
명시적 정정 큐, 같은 세션/턴 여부, 엣지 타입(정정 vs 다음 명령). §2의 턴 id가
그 재료의 절반이다.

## 12. 문헌의 처방을 실제로 재봤다 — 볼록 결합은 이 코퍼스의 헤드에서 진다

§10의 문헌 대조 뒤 남은 질문은 하나였다. **"고정 가중 RRF를 쓰는 것 자체가 틀렸나?"**
Bruch et al.은 정규화 점수의 **볼록 결합(CC)이 RRF보다 낫다**고 하고, 우리가 찾은 벽은
정확히 그들이 말한 RRF의 비평활성이다. 그래서 재봤다.

### 왜 CC가 벽을 없애는지 (산수)

RRF는 레인에 든 문서에 **바닥값을 항상 준다** — 꼴찌여도 `0.85/(60+50)`이다.
정규화 점수는 그 레인의 꼴찌를 **정확히 0**으로 만든다.

| | 가중 RRF | 정규화 CC |
|---|---|---|
| BM25 1위 · 벡터 없음 | 0.0025 | **0.15** |
| BM25 없음 · 벡터 50위 | 0.0077 | **~0.00** |
| BM25 없음 · 벡터 1위 | 0.0139 | 0.85 |

**새 상수가 없다** — α는 지금의 질의 타입 가중치를 그대로 쓴다. §10에서 실패한
"가중치를 옮기는" 실험들과 다른 이유가 이것이다.

### 실측 — 메모리 레인에서 정답의 순위 (Set A 20문항)

| | RRF (현행) | CC (min-max) | CC (z-score) |
|---|---|---|---|
| 헤드 개선 | — | C1 5→3 · C16 2→1 | C1 5→3 · C16 2→1 |
| **헤드 악화** | — | **C2 1→3 · C3 5→10 · C6 3→6 · C13 1→2 · C14 1→5 · C15 2→5 · C17 3→9 · C19 2→8** | **C3 5→10 · C6 3→6 · C13 1→2 · C14 1→4 · C15 2→5 · C17 3→9 · C19 2→8** |
| 꼬리 개선 | — | C7 52→45 · C11 63→51 · C18 51→26 · C20 52→36 | C7 52→35 · C18 51→21 · C20 52→41 |

**두 정규화가 같은 그림을 그린다** — 정규화 선택의 문제가 아니라 코퍼스의 성질이다.
CC는 **깊은 꼬리에서 낫고 헤드에서 확실히 나쁘다.** 그리고 꼬리는 §10의 어휘 슬롯이
이미 더 잘 처리한다 — 슬롯은 BM25 #1을 **7위**에 놓는데 CC는 #21~#41에 놓는다.

### 판정 — 채택하지 않는다. 다만 이유가 "안 봤다"가 아니다

- **기각 근거는 레인 단독 시뮬레이션이다.** 주의사항 #1대로 이건 end-to-end를
  예측하지 못한다. 그런데 헤드 악화가 두 정규화 모두에서 8문항·6문항이라
  **end-to-end 빌드를 쓸 이유가 없을 만큼 크다.** 이 판정은 그 근거로 내렸다.
- **문헌이 틀렸다는 뜻이 아니다.** Bruch의 결과는 BEIR 계열 웹·QA 코퍼스의 평균이고,
  여기는 한 사람이 쓴 한국어 대화 기록이다. 우리 코퍼스에서는 **헤드에 관한 한
  벡터 편향 RRF가 실제로 좋다** — 이 라인이 §10에서 다섯 번 확인한 것과 같은 방향이다.
- **아직 안 해 본 처방이 하나 남았다**: vstash의 **질의별 적응 가중치**. §10에서
  기각한 것은 *전역* 가중치 이동이고, CC로 기각한 것은 *융합 함수*다.
  "질의마다 다른 α"는 둘 다 아니고, 두 실패가 그 방향을 가리킨다 —
  어휘가 옳은 질의(C18)와 벡터가 옳은 질의(C14)가 한 코퍼스에 섞여 있다.

**요약**: 융합 함수는 바꾸지 않는다. 바꿀 이유를 못 찾아서가 아니라, **권고된 대체물을
실제로 재봤더니 우리 헤드에서 졌기 때문이다.** 남은 방향은 α를 질의마다 정하는 것이다.

## 13. 질의별 적응 가중치 — 신호가 없어서 접었다

§12에서 남겨 둔 마지막 문헌 처방이다(vstash). 만들기 전에 **신호가 두 부류를 가르는지**
부터 쟀다 — §11에서 DF로 배운 순서다.

Set A 20문항을 "정답이 더 앞선 레인"으로 라벨(LEX 8 · VEC 9 · 동률 3)하고, 질의 시점에
관측 가능한 후보 신호 넷의 판별력을 AUC로:

| 신호 | AUC |
|---|---|
| BM25 레인 clarity `(s₁−mean)/std` | 0.56 |
| 벡터 레인 clarity | 0.39 |
| 질의 평균 IDF (vstash의 신호) | 0.53 |
| 질의 최대 IDF | 0.41 |
| clarity 차이 (bm − vec) | **0.64** |

**전부 동전던지기 근처다.** 최고 0.64도 n=8/9에서 표준오차 ~0.14라 1σ 안이고,
중앙값도 겹친다(LEX meanIDF 3.39 vs VEC 3.16, maxIDF는 양쪽 5.52).

**왜 vstash와 다른가**: 그쪽 이득은 질의 특이성이 넓게 분포하는 BEIR 웹·QA 코퍼스에서
나온다. 여기는 **한 사람이 같은 문체로 쓴 한국어 회상 질문**이라 질의 간 분산 자체가
거의 없다 — 신호가 없는 게 아니라 이 코퍼스에서 **상수에 가깝다**.

**한계**: 라벨된 질의가 17개다. "이 표본에서 검출되지 않는다"이지 "없다"가 아니다.
되살리려면 라벨된 질의를 30~50개로 늘려 AUC를 다시 재라 — 0.64가 유지되면 신호이고,
0.5로 수렴하면 이 코퍼스에는 없는 것이다.

**이로써 문헌의 융합 처방 셋이 모두 닫혔다** (A 전역 가중치 · B 융합 함수 · C 적응
가중치). 조사 기록은 `docs/studies/2026-09-11-hybrid-fusion.md`로 옮겨 정리했다.
