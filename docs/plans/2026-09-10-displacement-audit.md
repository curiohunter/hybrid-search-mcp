# 무엇을 지웠는가 — 골드셋이 아니라 계측기를 만들었다

**작성** 2026-09-10 · **상태** 구현·측정 완료 · **선행** `docs/plans/2026-09-09-korean-morphology-backend.md`

---

## §1. 문항을 더 쓰는 건 답이 아니었다

인계 문서의 최우선 항목은 "Set A 골드셋 커버리지"였다. 209건의 잘못된 대체가
사라져도 20문항 중 하나도 안 움직이니 문항이 부족하다는 진단이었다.

그런데 **문항을 40개로 늘려도 같은 문제가 남는다.** 다음 사고는 다른 곳에
떨어지기 때문이다. 진짜 문제는 문항 수가 아니라 **재는 대상**이었다:

> `benchmarks/`의 모든 러너가 "답이 나왔는가"를 묻는다.
> **"갖고 있던 답을 지웠는가"를 묻는 러너가 하나도 없다.**

이 프로젝트를 가장 아프게 한 두 사고가 정확히 그 종류다. 9/9 §12(통합 노트가
통합 노트를 대체), 9/9 §8(셸 붙여넣기가 진짜 답을 대체). 둘 다 손으로 찾았고,
둘 다 Set A·Set B·코드축 어디에도 안 잡혔다.

## §2. 골드셋 없이 재는 두 가지 생각

**① 코퍼스가 자기 자신의 문항이다.** qa 레코드는 전부 자기가 답한 질문을 갖고
있다. 그 질문을 도로 물어보면 된다. **자기 질문으로 자기를 못 찾으면** 그건
라벨링이 필요 없는 결함이고, 문항 수는 레코드 수만큼 있다(2,000+).

**② 손상은 점수가 아니라 diff다.** 같은 질의를 두 번 돌린다 — supersession
매핑을 켠 채로, 그리고 비운 채로. 끈 쪽에 있는데 켠 쪽에 없으면 그건 정정이
**밀어낸** 것이다. 밀어내는 것 자체는 설계고, 그 과정에서 **질의의 단어를
잃는 것**은 설계가 아니다.

`benchmarks/displacement_audit.py`. 골드셋을 안 쓰므로 커밋할 것이 러너뿐이고
(측정 대상의 발화가 문항이 된다 — `CLAUDE.md`), **얼린 스냅샷에만** 돌린다:
두 번째 패스를 위해 supersession 테이블을 비웠다가 복원하기 때문이다.

측정을 오염시키지 않도록 두 가지를 구분한다:

- **맵이 지운 것** — 밀려난 청크가 저장된 매핑의 키인 경우. 파괴적 경로.
- **순위 흔들림** — 한계선 근처에서 밀린 것. 노이즈. 세지 않고 보고만 한다.
  (실측에서 0건이었다 — 즉 밀려난 것은 전부 맵이 지운 것이었다.)

## §3. 첫 실행에서 나온 것

도그푸딩 코퍼스, 무작위 120개 레코드를 자기 질문으로 조회:

| | 값 |
|---|---|
| 자기회수, 맵 **끔** | 114/120 (95%) |
| 자기회수, 맵 **켬** | **101/120 (84%)** |
| **맵이 깎아먹은 자기회수** | **13건** |
| 맵이 지운 매치가 있는 질의 | 27/120 (22%) |
| 순위 흔들림 | 0 |

**supersession이 순이익이 아니었다.** 자기 질문을 물었을 때 그 레코드를
지우는 일이 다섯 번에 한 번꼴이었다.

사례를 읽으면 변명의 여지가 없다. **질의문과 글자 그대로 같은 레코드가
사라지고** 무관한 턴이 그 자리에 들어간다. 어떤 턴의 문장을 그대로 붙여넣어
물어도 그 턴이 결과에서 지워지고, 같은 날 오간 다른 지시 턴이 대신 온다.
본 레포 인덱스에서도 같은 것이 나왔다 — 계획 다음 단계를 묻는 턴이 무관한
커밋 지시 턴으로 대체됐다. (원문은 옮기지 않는다 — `CLAUDE.md`. 실물은
리포트에서 볼 것.)

**다만 자기회수 손실이 곧 손상은 아니다.** 진짜로 더 새로운 답이 낡은 답을
대체하는 것은 이 기능의 목적이다. 그래서 도구는 "대체가 질의의 단어를
잃었는가"를 같이 보고하고, **사례를 읽으라고 출력에 적어 둔다.** 숫자만
믿으면 안 되는 지표다.

## §4. 수정 — 사용자가 지목한 레코드는 지우지 않는다

splice는 정원이 차면 낡은 히트를 **교체**한다. 그게 파괴적 모서리다.

교체가 맞는 경우는 사용자가 낡은 답에 **우연히 걸린** 때다. 사용자가 그
레코드를 **지목한** 때는 다르다 — 그때 "정정"을 주는 것은 **아무도 안 물어본
질문에 답하고, 물어본 것은 없애는** 일이다.

`_ASKED_FOR_THIS_OVERLAP = 0.8`. 질의가 그 레코드의 자기 질문과 겹침 0.8 이상이면
**교체 금지**. 노출까지 막지는 않는다 — 자리가 남으면 정정은 그 위에 삽입되고
둘 다 보인다. 막는 것은 **삭제**뿐이다.

| | 수정 전 | 수정 후 |
|---|---|---|
| 자기회수, 맵 켬 | 101/120 (84%) | **115/120 (96%)** |
| 자기회수, 맵 끔 | 114/120 (95%) | 114/120 (95%) |
| 맵이 지운 매치 | 27/120 (22%) | **14/120 (12%)** |
| Set A found / **top3** / MRR | 0.75 / **0.70** / 0.571 | **동일** |
| Set B found | 0.05 | **동일** |
| 코드축 top5 / recall / memory@3 | 0.92 / 0.77 / 0.16 | **동일** |
| 테스트 | 1,755 | 1,759 |

**맵 켬(115)이 맵 끔(114)을 처음으로 넘어섰다.** supersession이 이제
자기회수를 깎지 않고 아주 조금 보탠다.

기존 세 축은 **소수점까지 그대로**다. 즉 이 수정은 기존 계측으로는
**존재하지 않는 변경**이고, 새 계측으로는 큰 개선이다. 그것이 §1의 논지를
그대로 증명한다 — 못 재던 것을 재게 되니 고칠 것이 보였다.

## §5. 남은 것

1. **12%는 아직 남아 있다.** 지목하지 않은 질의에서 맵이 매치를 지우는 경우다.
   전부 손상은 아니다(정당한 정정이 섞여 있다). 다음은 이 14건을 사람이 읽고
   정당/손상을 가르는 것이고, 그 라벨이 붙으면 비율이 아니라 **정확도**로
   말할 수 있다.
2. **자기회수 95%의 나머지 5%.** 맵과 무관하게 자기 질문으로 자기를 못 찾는
   레코드다. 질문 자체가 지나치게 일반적이라 다른 레코드에 밀리는 경우가
   많아 결함이 아닐 수 있다. 표본을 읽고 가려야 한다.
3. **다른 프로젝트에서 돌려볼 것.** 지금 수치는 코퍼스 하나짜리다.
4. **`_ASKED_FOR_THIS_OVERLAP = 0.8`은 아직 스윕하지 않았다.** 0.8은 "사실상
   같은 질문"을 뜻하는 보수적인 값으로 고른 것이고, 코퍼스 신호(자기회수)와
   기존 3축을 둘 다 놓고 훑으면 더 나은 지점이 있을 수 있다.

## §6. 재현

```bash
# 얼린 스냅샷에만. 두 번째 패스를 위해 supersession 테이블을 비웠다 복원한다.
python benchmarks/displacement_audit.py --config $SNAP/config.toml \
    --project <이름> --sample 120 --out /tmp/displacement.json
```

출력의 숫자 두 개만 보면 된다 — **맵이 깎아먹은 자기회수**(음수여야 한다)와
**맵이 지운 매치의 비율**. 그리고 리포트의 사례를 읽을 것. 도구가 출력에
그렇게 적어 둔 이유가 있다.
