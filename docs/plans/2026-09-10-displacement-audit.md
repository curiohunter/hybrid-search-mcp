# 무엇을 지웠는가 — 골드셋이 아니라 계측기를 만들었다

**작성** 2026-09-10 · **상태** 구현·측정 완료 · **선행** `docs/plans/2026-09-09-korean-morphology-backend.md`

---

## §1. 문항을 더 쓰는 건 답이 아니었다

인계 문서의 최우선 항목은 "Set A 골드셋 커버리지"였다. 209건의 잘못된 대체가
사라져도 20문항 중 하나도 안 움직이니 문항이 부족하다는 진단이었다.

그런데 **문항을 40개로 늘려도 같은 문제가 남는다.** 다음 사고는 다른 곳에
떨어지기 때문이다. 진짜 문제는 문항 수가 아니라 **재는 대상**이었다:

> `benchmarks/`의 모든 러너가 "답이 나왔는가"를 묻는다.
> **"갖고 있던 답을 지웠는가"를 묻는 러너가 하나도 없다.**

이 프로젝트를 가장 아프게 한 두 사고가 정확히 그 종류다. 9/9 §12(통합 노트가
통합 노트를 대체), 9/9 §8(셸 붙여넣기가 진짜 답을 대체). 둘 다 손으로 찾았고,
둘 다 Set A·Set B·코드축 어디에도 안 잡혔다.

## §2. 골드셋 없이 재는 두 가지 생각

**① 코퍼스가 자기 자신의 문항이다.** qa 레코드는 전부 자기가 답한 질문을 갖고
있다. 그 질문을 도로 물어보면 된다. **자기 질문으로 자기를 못 찾으면** 그건
라벨링이 필요 없는 결함이고, 문항 수는 레코드 수만큼 있다(2,000+).

**② 손상은 점수가 아니라 diff다.** 같은 질의를 두 번 돌린다 — supersession
매핑을 켠 채로, 그리고 비운 채로. 끈 쪽에 있는데 켠 쪽에 없으면 그건 정정이
**밀어낸** 것이다. 밀어내는 것 자체는 설계고, 그 과정에서 **질의의 단어를
잃는 것**은 설계가 아니다.

`benchmarks/displacement_audit.py`. 골드셋을 안 쓰므로 커밋할 것이 러너뿐이고
(측정 대상의 발화가 문항이 된다 — `CLAUDE.md`), **얼린 스냅샷에만** 돌린다:
두 번째 패스를 위해 supersession 테이블을 비웠다가 복원하기 때문이다.

측정을 오염시키지 않도록 두 가지를 구분한다:

- **맵이 지운 것** — 밀려난 청크가 저장된 매핑의 키인 경우. 파괴적 경로.
- **순위 흔들림** — 한계선 근처에서 밀린 것. 노이즈. 세지 않고 보고만 한다.
  (실측에서 0건이었다 — 즉 밀려난 것은 전부 맵이 지운 것이었다.)

## §3. 첫 실행에서 나온 것

도그푸딩 코퍼스, 무작위 120개 레코드를 자기 질문으로 조회:

| | 값 |
|---|---|
| 자기회수, 맵 **끔** | 114/120 (95%) |
| 자기회수, 맵 **켬** | **101/120 (84%)** |
| **맵이 깎아먹은 자기회수** | **13건** |
| 맵이 지운 매치가 있는 질의 | 27/120 (22%) |
| 순위 흔들림 | 0 |

**supersession이 순이익이 아니었다.** 자기 질문을 물었을 때 그 레코드를
지우는 일이 다섯 번에 한 번꼴이었다.

사례를 읽으면 변명의 여지가 없다. **질의문과 글자 그대로 같은 레코드가
사라지고** 무관한 턴이 그 자리에 들어간다. 어떤 턴의 문장을 그대로 붙여넣어
물어도 그 턴이 결과에서 지워지고, 같은 날 오간 다른 지시 턴이 대신 온다.
본 레포 인덱스에서도 같은 것이 나왔다 — 계획 다음 단계를 묻는 턴이 무관한
커밋 지시 턴으로 대체됐다. (원문은 옮기지 않는다 — `CLAUDE.md`. 실물은
리포트에서 볼 것.)

**다만 자기회수 손실이 곧 손상은 아니다.** 진짜로 더 새로운 답이 낡은 답을
대체하는 것은 이 기능의 목적이다. 그래서 도구는 "대체가 질의의 단어를
잃었는가"를 같이 보고하고, **사례를 읽으라고 출력에 적어 둔다.** 숫자만
믿으면 안 되는 지표다.

## §4. 수정 — 사용자가 지목한 레코드는 지우지 않는다

splice는 정원이 차면 낡은 히트를 **교체**한다. 그게 파괴적 모서리다.

교체가 맞는 경우는 사용자가 낡은 답에 **우연히 걸린** 때다. 사용자가 그
레코드를 **지목한** 때는 다르다 — 그때 "정정"을 주는 것은 **아무도 안 물어본
질문에 답하고, 물어본 것은 없애는** 일이다.

`_ASKED_FOR_THIS_OVERLAP = 0.8`. 질의가 그 레코드의 자기 질문과 겹침 0.8 이상이면
**교체 금지**. 노출까지 막지는 않는다 — 자리가 남으면 정정은 그 위에 삽입되고
둘 다 보인다. 막는 것은 **삭제**뿐이다.

| | 수정 전 | 수정 후 |
|---|---|---|
| 자기회수, 맵 켬 | 101/120 (84%) | **115/120 (96%)** |
| 자기회수, 맵 끔 | 114/120 (95%) | 114/120 (95%) |
| 맵이 지운 매치 | 27/120 (22%) | **14/120 (12%)** |
| Set A found / **top3** / MRR | 0.75 / **0.70** / 0.571 | **동일** |
| Set B found | 0.05 | **동일** |
| 코드축 top5 / recall / memory@3 | 0.92 / 0.77 / 0.16 | **동일** |
| 테스트 | 1,755 | 1,759 |

**맵 켬(115)이 맵 끔(114)을 처음으로 넘어섰다.** supersession이 이제
자기회수를 깎지 않고 아주 조금 보탠다.

기존 세 축은 **소수점까지 그대로**다. 즉 이 수정은 기존 계측으로는
**존재하지 않는 변경**이고, 새 계측으로는 큰 개선이다. 그것이 §1의 논지를
그대로 증명한다 — 못 재던 것을 재게 되니 고칠 것이 보였다.

## §5. 라벨링을 실제로 해봤다 — 그리고 결함이 두 개 더 나왔다

"남은 14건을 사람이 읽고 정당/손상을 가른다"고 적어놓고 말로만 두면 아무도
못 한다. 그래서 14건을 표로 뽑아 읽었다. **읽는 행위 자체가 두 가지를 잡았다.**

### 5.1 계측기 자체의 결함

표를 만들다 보니 "대체"로 표시된 것이 밀려난 것보다 **날짜가 더 오래된** 경우가
있었다. supersession은 최신으로만 매핑하므로 있을 수 없다 — 도구가 "대체"를
*실제 짝*이 아니라 *그 패스의 첫 삽입물*로 찍고 있었다. `saved[displaced_id]`로
짝을 정확히 맞춰야 한다. **표를 안 만들었으면 못 봤을 결함이다.**

### 5.2 역방향 매핑 18건은 버그가 아니었다

짝을 고치고 보니 오래된 것이 최신을 대체하는 매핑이 449건 중 18건(4%) 있다.
전부 **밀려난 쪽에 답변 excerpt가 없는** 경우였다 — §8의 "이기는 쪽은 답이
있어야 한다" 규칙이 의도대로 도는 모습이다. 시간은 역행하지만 의미는 맞다:
맨 턴 대신 그 질문에 답하는 레코드를 보여준다.

### 5.3 비율에 최소 질량이 없었다 — 진짜 결함

그런데 그 역방향 쌍들의 질문이 서로 하나도 안 닮았는데 겹침이 0.87이었다.
답변 없는 경로로 생긴 매핑 112건의 질문 토큰 질량을 재 보니:

| | 값 |
|---|---|
| 중앙값 | 7.0 |
| **10퍼센타일** | **2.0** |
| 질량 4.0 미만 | **29건 (25%)** |

토큰이 2개인 질문은 **어떤 비율 기준도 무의미하게 통과한다.** 2개 중 2개를
공유하면 "겹침 1.00"이지만 증거가 아니다. 실제로 `['가장','좋겠']`이
`['가장','좋겠']`과 1.00으로 묶여 있었다 — 일반적인 질문이 일반적인 질문과.

`_MIN_QUESTION_MASS = 4.0`을 만들고 **적용했다가 되돌렸다** (§6에서 다시
채택된다 — 그때는 진짜 원인을 같이 고쳤기 때문이다).

| | 기준선 | 질량 4.0 |
|---|---|---|
| 맵이 지운 매치 | 12% | **10%** |
| 자기회수 (맵 켬) | 96% | 96% |
| Set A found / top3 / MRR | 0.75 / 0.70 / 0.571 | 동일 |
| 코드축 | 0.92 / 0.77 / 0.16 | 동일 |
| **Set B found** | 0.05 | **0.02** |

파괴 지표는 좋아지는데 **Set B가 41문항 중 2개를 잃는다.** 목적함수에서 Set B는
하한 제약이므로 채택하지 않았다. 3.0으로 낮춰도 같은 문항을 잃는다 — 즉 손실이
가장 얇은 쌍에서 오는 게 아니다. **splice는 정정 장치이면서 노출 장치**라,
매핑을 끊으면 둘 다 끊긴다.

이 시점의 결론은 "비용은 있고 이득은 비율뿐"이었다. **§6이 그 판단을 뒤집는다** —
라벨을 붙이자 Set B가 잃던 문항이 damage 사례였고, 원인을 고치니 둘이 같이
좋아졌다.

**여기서 하나 배웠다.** 이 판정 중에 Set A가 0.68로 읽히고 **노이즈 바닥이
0.00 → 0.05**로 올라간 판독이 한 번 있었다. 오늘 모든 측정이 0.00이었으므로
이건 "나빠졌다"가 아니라 **측정이 오염됐다**는 신호였고, 깨끗하게 다시 재니
0.70 / 0.00으로 돌아왔다. 규약의 `--repeat`은 장식이 아니다.

이 항목은 인계 문서의 "미룬 것들"에 **"최소 절대 공유 질량 — 비율만으로는
증거가 안 된다"**로 몇 세션째 적혀 있었다. 막연한 백로그가 라벨링 한 번에
수치가 붙은 결함이 됐다.

## §6. 라벨을 다 붙였다 — 그리고 그게 구조적 결함을 꺼냈다

§5는 표를 만들어 읽기만 했다. 이번엔 **밀어냄 21건 전부에 라벨을 붙였다**
(`~/.hybrid-search/benchmarks/valuein_displacement_labels.json` — 근거가 실제
턴을 지목하므로 레포 밖).

**판정 기준 하나** (프로브와 무관하게 재사용되도록):
> 짝이, 밀려난 레코드와 **실질적으로 같은 질문**에 답하는가?
> `legitimate` = 같은 질문의 더 최신 답, 또는 답 없는 턴 → 그 질문에 답하는
> 레코드(설계된 경로). `damage` = 짝이 다른 질문에 답한다 → 밀려난 답은 사라진다.

**기준선 정밀도: 8/16 = 50%.** 밀어냄의 절반이 답을 파괴하고 있었다.

### 6.1 라벨이 고를 수 있게 해 준 것

라벨을 정렬해 보면 무엇이 damage를 가르는지 나온다:

| 분리자 | damage 차단 | legitimate 손실 |
|---|---|---|
| 질문 겹침 < 0.70 | 5/8 | 2/8 |
| 답없음 & 질량 < 4.0 | 2/8 | 1/8 |
| 둘 다 | **7/8** | 3/8 |

legitimate 8건 중 6건이 **거의 같은 문장의 재질문**이었다(겹침 1.00). 그래서
인덱스 시점 질문 기준을 `_SUPERSESSION_QUERY_OVERLAP = 0.70`으로 올렸다 —
질의 시점 값(접두 백엔드 0.30)은 질의가 이미 걸러 준 후보용이라 코퍼스
전체에는 너무 관대하다.

### 6.2 그런데 엄격화가 **손상을 만들었다** — 구조적 결함

기준을 올렸더니 매핑이 **35건 새로 생기고 33건이 짝이 바뀌었다.** 술어를
좁혔는데 새 매핑이 생기는 건 불가능해야 한다.

원인은 `_strict_group_indices` — **최신순 greedy 완전연결 묶음**에서 짝을
읽어내고 있었다. 간선 하나를 없애면 그룹이 쪼개지고, **자기 그룹의 승자였던
레코드가 다른 그룹에 들어가 한 번도 짝지어 본 적 없는 승자에게 매핑된다.**
새로 생긴 35건 중 하나가 골드 문항(B11)의 답을 지웠다.

**이것이 이 라인에서 임계값을 어느 방향으로 옮겨도 같은 문항을 잃던 이유다.**
지도가 술어에 대해 단조롭지 않았다.

**수정**: 짝을 그룹이 아니라 **쌍 단위**로 정한다 — "이 레코드와 같은 주제인
가장 최신 레코드". 최신순으로 훑어 첫 매치에서 멈춘다. 단조롭고(엄격화는
짝을 빼앗을 뿐 만들지 못한다), 연쇄 방지 규칙이 필요 없고(A는 A가 직접
매치한 것에만 매핑된다), splice가 실제로 묻는 질문에 답한다. 실측: 새로 생긴
매핑 **35건 → 0건**. 테스트가 이 성질을 지킨다.

단, 답 없는 레코드는 예외로 **더 오래된 답도** 받는다. 라벨에서 legitimate
8건 중 3건이 그 모양이었다 — 맨 턴을 친 사람에게 그 질문에 답하는 레코드를
건네는 것은 시간 역행이어도 맞다.

### 6.3 마지막 damage — 포함은 유사가 아니다

단조성을 고친 뒤에도 B11이 안 돌아왔다. 그 쌍을 라벨링해 보니 damage이고,
원인이 새로웠다: 밀려난 쪽 질문이 **긴 붙여넣기 블록**이라 짧은 질문이 통째로
포함돼 겹침이 **1.00**이었다.

`weighted_overlap`은 **가벼운 쪽**으로 나눈다. 질의 시점에는 맞다(짧은 질의가
긴 레코드의 일부와 맞으면 히트다). 코퍼스 전체에서는 **포함을 동일로 읽는다**,
그리고 qa 코퍼스에는 붙여넣기가 널려 있다.

남은 쌍들의 **대칭 겹침**(공유 / 무거운 쪽)을 재 보니 깨끗하게 갈렸다:

```
damage      0.07  0.21  0.29  0.29
legitimate  0.19  0.36  0.38  0.50  0.92  1.00  1.00  1.00  1.00
```

`_MIN_SYMMETRIC_QUESTION_OVERLAP = 0.33` — 그 틈에 놓으면 **남은 damage 4건을
전부 막고 legitimate 1건**을 잃는다.

### 6.4 결과

| | 기준선 | 최종 |
|---|---|---|
| **밀어냄 정밀도** (전건 라벨) | 8/16 = **50%** | 8/8 = **100%** |
| **damage 건수** | 8 | **0** |
| 맵이 지운 매치 | 12% (14/120) | **6% (7/120)** |
| 자기회수 (맵 켬 / 끔) | 96% / 95% | 96% / 95% |
| Set A found / **top3** / MRR | 0.75 / **0.70** / 0.571 | **동일** |
| **Set B found** | 0.05 | **0.05** |
| 코드축 top5 / recall / memory@3 | 0.92 / 0.77 / 0.16 | **동일** |
| 저장 매핑 | 452 | 187 |
| 테스트 | 1,760 | 1,762 |

**§5의 트레이드오프가 사라졌다.** 거기서는 "밀어냄 지표는 원하고 Set B는
거부한다, 둘 다 비율이라 못 가린다"였다. 라벨이 붙자 Set B가 잃던 그 문항이
**damage 사례였음**이 드러났고, 진짜 원인(비단조 묶음 + 포함≠유사)을 고치니
**둘이 동시에 좋아졌다.** 두 지표가 반대를 가리킬 때는 대개 한쪽이 옳은 것이
아니라, 아직 원인을 못 찾은 것이다.

---

## §7. 재현율 — 정밀도만 재면 아무것도 안 하는 게 만점이다

밀어냄 정밀도를 100%로 만드는 가장 쉬운 방법은 **아무것도 안 대체하는 것**이다.
그래서 반대쪽을 재는 도구를 붙였다 — `benchmarks/supersession_recall.py`.
현행 맵을 **인덱스 시점 바를 끈 같은 알고리즘**과 비교하고, 잘라낸 매핑을
**어느 바가 잘랐는지**까지 붙여서 보여준다. 과하게 조인 바가 총합이 아니라
바 단위로 드러난다.

### 7.1 매핑 수준

바를 다 켠 상태에서 **557건을 잘랐다**(688 → 187). 층화 표본 24건을 읽고
밀어냄과 **같은 기준**으로 라벨링했다(레포 밖, `valuein_cut_labels.json`):

| 바 | 자른 수 | 라벨 | 진짜 정정 손실 |
|---|---|---|---|
| 질문 겹침 (0.70) | 474 | 8 | 25% |
| 대칭 겹침 | 42 | 7 | **57%** |
| 질량(답없음) | 41 | 8 | 25% |
| **합계** | **557** | 23 | **35%** |

### 7.2 프로브 수준 — 손실이 실제로 결과에 닿는가

매핑을 잘라도 그 레코드가 검색에 안 뜨면 비용이 0이다. 그래서 같은 프로브
120개를 **두 맵으로 각각** 돌려 비교했다: **40건(33%)이 느슨한 맵에서는 받던
정정을 현행에서는 못 받는다.** 잘라낸 것의 35%가 진짜였으니 대략 **여덟 중
하나가 진짜 정정을 잃는다.** 바가 너무 조였다.

### 7.3 질문 겹침 바는 중복이었다

가장 많이 자르는 바(474/557)를 **질의 시점 값으로 되돌려** 봤다:

| | 바 0.70 | 바 제거 |
|---|---|---|
| 밀어냄 정밀도(라벨) | 100% (8/8) | **100% (9/9)** |
| 저장 매핑 | 187 | **258** |
| 프로브 재현율 손실 | 33% | **31%** |
| Set A / Set B / 코드축 | — | **전부 불변** |

**정밀도를 하나도 잃지 않고 매핑 71건이 돌아온다.** 대칭·질량 바가 이미 같은
damage를 잡고 있었다 — 질문 바는 세금이었다. 제거했다.

**교훈은 순서에 관한 것이다.** 라벨만 놓고 보면 질문 겹침이 단독 분리자로는
제일 좋아 보였다(damage 5/8 차단). 실제로는 대칭 겹침이 재는 것과 **같은
실패를 더 나쁜 각도에서** 재고 있었다. 분리자를 하나씩 고르지 말고, 넣은 뒤에
**나머지가 여전히 값을 하는지** 다시 볼 것.

### 7.4 지금 남은 재현율 비용

대칭 겹침 바가 467건을 자르고 그중 **40%가 진짜 정정**이다. 다만 임계값으로는
못 줄인다 — 0.29 아래로 내리면 damage가 되돌아온다(§6.3의 분리표). **더 나은
특징이 필요하지 임계값 이동으로 풀리는 문제가 아니다.**

라벨이 23건뿐이라 여기서 더 조율하면 픽스처 과적합이다. 멈춘다.

## §8. 남은 것

1. **대칭 겹침 바의 재현율 비용(467건 중 40%)** — §7.4. 임계값으로는 못 푼다.
   더 나은 특징을 찾거나, 밀어냄이 아니라 **삽입**으로 전환하는 길이 있다:
   자리가 남을 때는 이미 정정을 교체가 아니라 삽입한다. 정원이 찼을 때도
   교체 대신 포기하면 재현율 비용이 사라지고 정밀도는 그대로다 — 대신 낡은
   답이 그대로 남는다. 잴 수 있는 질문이다.
2. **`_ASKED_FOR_THIS_OVERLAP`(0.8)은 아직 스윕하지 않았다.** 라벨이 있으니
   이제 제대로 고를 수 있다.
3. **다른 프로젝트에서 돌려볼 것.** 라벨과 임계값 모두 코퍼스 하나짜리다.
2. **자기회수 95%의 나머지 5%.** 맵과 무관하게 자기 질문으로 자기를 못 찾는
   레코드다. 질문 자체가 지나치게 일반적이라 다른 레코드에 밀리는 경우가
   많아 결함이 아닐 수 있다. 표본을 읽고 가려야 한다.
3. **다른 프로젝트에서 돌려볼 것.** 지금 수치는 코퍼스 하나짜리다.
4. **`_ASKED_FOR_THIS_OVERLAP = 0.8`은 아직 스윕하지 않았다.** 0.8은 "사실상
   같은 질문"을 뜻하는 보수적인 값으로 고른 것이고, 코퍼스 신호(자기회수)와
   기존 3축을 둘 다 놓고 훑으면 더 나은 지점이 있을 수 있다.

## §9. 재현

**둘 다 얼린 스냅샷에만.** 두 도구 모두 supersession 테이블을 임시로 바꿨다
복원한다.

```bash
# 정밀도 — 맵이 지운 것 중 몇 건이 답을 파괴했나
python benchmarks/displacement_audit.py --config $SNAP/config.toml \
    --project <이름> --sample 120 --labels <라벨.json> --out /tmp/disp.json

# 재현율 — 바가 거절한 정정 중 몇 건이 진짜였나 (+ 프로브 수준까지)
python benchmarks/supersession_recall.py --config $SNAP/config.toml \
    --project <이름> --sample 24 --out /tmp/cut.json      # 읽을 표본
python benchmarks/supersession_recall.py --config $SNAP/config.toml \
    --project <이름> --labels <컷라벨.json> --probe 120    # 채점
```

**한쪽만 보면 반드시 속는다.** 정밀도만 재면 아무것도 안 대체하는 게 만점이고,
재현율만 재면 전부 대체하는 게 만점이다.

출력의 숫자 두 개만 보면 된다 — **맵이 깎아먹은 자기회수**(음수여야 한다)와
**맵이 지운 매치의 비율**. 그리고 리포트의 사례를 읽을 것. 도구가 출력에
그렇게 적어 둔 이유가 있다.
