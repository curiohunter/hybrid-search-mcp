**작성** 2026-09-08 · **상태** 파일럿 착수 · **선행**

## 0. 한 문장

코드 레인은 tree-sitter가 경계를 정해 줘서 "답이 들어 있는 단위"로 검색되는데,
**기억 레인(대화·qa·카드)은 한 번도 파싱된 적이 없어 통짜 덩어리로 검색된다.**
그 결과 물어본 사실이 청크의 1~2%일 때 두 검색기 모두 그것을 못 본다.

## 1. 근거 (전부 실측, `2026-09-04-...` §16)

| 실험 | 결과 |
|---|---|
| (a) 리랭커 천장 | Set B 목표의 **6/10이 회수된 50행 풀 밖** → 어떤 재정렬도 0.40을 못 넘는다 |
| (a) 부정 가설 | **기각.** 부정 문항의 질의-문서 코사인이 다른 범주와 같다(0.461 / 0.477 / 0.493) |
| (a) 희석 | cos(질의,**문장**) > cos(질의,**청크**)가 전 범주에서 성립 (평균 0.474 → 0.556) |
| (b) 문장 색인 + 부모 반환 | 부모 top-3 **0/10 → 6/10**, top-10 3/10 → 8/10 |
| (c) 반환 폭 확대 | 음성. Set A 무변동, Set B는 k=4에서 +1문항에 질의당 29k자 |
| (d) 문장 어휘 max 재정렬 | 음성 — (a)의 예측대로 재정렬은 풀을 못 이긴다 |

라운드 3~5의 랭킹 규칙 6종도 전부 0이었다. **순서가 아니라 회수가 병목이다.**

## 2. 설계 (심사 반영본)

1. **구조 기반 claim 분할.** 구두점이 아니라 그 소스의 문법으로: 코드펜스·셸
   출력 제거 → 굵게 표시된 주장 / 표 행 / 번호·불릿 항목 / 사용자 요청 →
   나머지 산문은 문단 단위. `node_type='claim'`.
2. **자식은 기존 `chunks` 테이블의 행.** 별도 저장소를 만들지 않는다. 부모
   포인터는 기존 `file_id` + 새 `parent_name`. 3저장소 일관성 검사, 슬롯
   플래너, 레인 분리, 품질 게이트가 그대로 작동한다.
3. **2단계 풀** (심사 #1). 상위 **N claim** 회수 → 부모로 폴딩 → 상위
   **50 부모** enrich. claim 단위로 50행만 자르면 부모가 6~10개로 줄어
   지금보다 다양성이 **떨어진다**.
4. **집계 함수는 정하지 않았다** (심사 #4). max는 자식이 많은 부모에 편향된다
   (`memory_card`는 파일 통째라 길이 무제한). max / top-k 평균 / node_type별
   정규화를 스윕해서 정한다.
5. 표시 단위는 여전히 부모(턴·파일). 사용자에게 보이는 것은 안 바뀐다.

## 3. 불변식

1. **증류는 원시를 대체하지 않는다.** 통제 실험에서 verbatim 43.9% → LLM 추출
   28.0% (arXiv 2601.00821). 동거만 허용한다.
2. **스토리지 변경 전에 P2까지 끝낸다.** P2 결과에 따라 설계가 반으로 준다.
3. **집계 숫자에는 신뢰구간을 붙인다** (심사 #2). 재실행 스프레드 0.00은
   결정성이지 표본오차가 아니다. 질의별 귀속이 있는 변화와 집계만 있는
   변화를 구분해 적는다.
4. 골드셋·결과물은 레포에 두지 않는다 (`CLAUDE.md`).

## 4. 파일럿 — 싼 것부터

### P0. 골드셋 확대 (Set B 10→30, Set A 15→30)

n=10에서 1문항 = 0.10이라 지금까지의 모든 델타가 표본오차 안에 있다.
30이라고 유의해지는 것은 아니지만 1문항이 0.033이 되고, 결론이 특이한
몇 문항에 얹혀 있을 확률이 줄어든다.

**방법 (기계적, 기존 절차 그대로)**
- Set B: conv_turn에 1~3회 등장하고 **비-conv 청크에는 0회**인 18~46자 문장을
  seed 고정 표본에서 뽑아, 잡담이 아니라 사실인 것만 남긴다.
- Set A: qa_log/consolidated/memory_card에 있고 **conv_turn에는 0회**인 구절.
  질문은 그 기록의 프론트매터 질의를 **패러프레이즈**한다(원문 그대로 쓰면
  어휘 레인에 답을 넘겨주는 것이다).

**완료 판정 (기계 검증)**
```bash
python benchmarks/verify_conv_gold.py --gold ~/.hybrid-search/benchmarks/valuein_conv_gold_rawonly.json
python benchmarks/verify_conv_gold.py --gold ~/.hybrid-search/benchmarks/valuein_conv_gold.json
```
- 두 세트 각 **문항 수 ≥ 30**
- Set B: `unreachable 0`, 그리고 **모든 구절이 single lane (raw)**
- Set A: `unreachable 0`, 그리고 **모든 구절이 single lane (distilled)**
- 확대 후 **현재 코드로 기준선을 다시 잰다** — 이전 10/15문항 수치와
  섞어 쓰지 않는다.

### P1. 구조 splitter 분포 측정

턴당 5~8개는 근거 없이 지어낸 숫자였다(심사 #8). 먼저 잰다.

**산출물**: 무작위 200턴(seed 고정)에 splitter를 돌려
- claim/턴 **중앙값·p90·최대**
- claim당 **문자 수** 중앙값·p90
- claim 0개가 나오는 턴의 비율
- 품질 게이트가 제거하는 claim 비율 (심사 #9)

**판단 규칙**: 중앙값이 **15 이상**이면 구조 split이 구두점 split과 다르지
않다는 뜻이고, "자식 수 1/4"이라는 비용 논거는 폐기한다.

**순서 고정** (심사 #9): 코드펜스·셸 출력 제거 → claim 생성 → 품질 게이트.

### P2. claim 단위 BM25만 — 임베딩 0원 (갈림길)

(b)는 **벡터만** 썼다. claim 단위 **어휘** 검색만으로 얼마가 오는지 잰 적이
없는데, tantivy 삽입에는 임베딩이 필요 없다. 여기서 대부분이 오면 46분·346MB가
통째로 사라진다.

**방법**: 프로덕션 인덱스를 건드리지 않고 **임시 tantivy 인덱스**를 스크래치에
짓는다(claim만). 질의마다 상위 N claim → 부모 폴딩(max) → 부모 순위.

**보고 형식** (심사 #7 — 분리해서 적는다)
```
arm            found  top3   MRR   (95% CI)
chunk BM25     …      …      …
claim BM25     …      …      …
claim vector   …      …      …      ← (b) 재사용
claim RRF      …      …      …
```

**판단 규칙**
- claim BM25만으로 부모 top-3가 chunk 기준보다 **+0.20 이상**이면 → 벡터
  없이 가는 설계를 먼저 검토한다(비용이 거의 0).
- 벡터가 있어야만 오르면 → P3로 가되 임베딩 비용을 설계에 명시한다.

### P3. 2단계 풀 + 집계 함수 스윕

- N claim ∈ {100, 300, 1000} × 집계 ∈ {max, top-3 평균, node_type 정규화}
- 지표: 부모 top-3 / top-10, 그리고 **부모 다양성**(상위 50에 든 서로 다른
  부모 수) — 심사 #1이 지적한 퇴화를 직접 감시한다.

### P4. Set A 미스 병인 라벨링

확대된 Set A에서 못 찾는 문항 각각에 대해 실패 단계를 라벨링한다:
**풀 누락 / 랭킹 손실 / enrich 누락 / 정답이 코퍼스에 없음.**
이 표가 나오기 전에는 기억 레인 전체로 넓히지 않는다 (심사 #5).

## 8. 실행 기록

### P0 — 골드셋 확대 ✅ (2026-09-08)

**결과**: Set B 10 → **41**, Set A 15 → **20**.

**계획과 달라진 것 ①: 검증기에 모델링 오류가 있었다.**
`verify_conv_gold.py`가 모든 `qa_log`를 "증류"로 취급했는데, Stop 훅이 쓴
`qa/YYYY/MM/*`는 그 턴을 거의 그대로 복사한 것이라 **증류물이 아니다.**
그래서 원시 전용 사실이 "레인 혼재"로 잘못 찍혔다 — 품질 게이트를 통과한
모든 턴에서 구조적으로 그렇게 된다(전사와 그 전사로 쓴 로그에 같은 문장이 있다).
검증기를 경로 인식으로 고쳤다: `qa/consolidated/`만 증류, `qa/YYYY/`는 원시.

**계획과 달라진 것 ②: Set A는 30에 못 간다.**
증류물이 통합 노트 20건 + 실사용 메모리 카드 3건뿐이다. qa 답변 발췌를
소스로 12문항을 만들었는데 자동 분류 결과 **전부 원시 레인**이라 Set B로
옮겼다. Set A는 20(=통합 노트 전량)이 이 코퍼스의 천장이다.

**계획과 달라진 것 ③: 완료 판정을 정정했다.**
"Set A 모든 구절이 single lane (distilled)"는 달성 불가다 — 통합 노트는
대화의 표현을 인용하므로 그 구절이 원시 레인에도 있다. 실질 기준으로 바꿨다:
**문항마다 최소 한 구절이 증류물에 있을 것.** 20문항 전부 충족(순수 12,
증류-포함-혼재 8).

**기계 검증**
```
Set B(41): unreachable 0 · single lane 44 · BOTH lanes 0
Set A(20): unreachable 0 · 문항별 증류 보유 20/20
```
(원시 전용을 어기던 B39는 커밋된 문서(`section`)에도 같은 문장이 있어 뺐다.)

`--repeat 3`, 얼린 스냅샷, in-flight off, Wilson 95% CI 동반.

| | 이전 (n=10 / 15) | **확대 후 (n=41 / 20)** |

| Set B answer_found | 0.30 | **0.15** [0.07, 0.28] |

재실행 스프레드(결정성)와 표본오차를 같은 화면에서 구분해 읽게 했다.

### P1 — 구조 splitter 분포 ✅ (2026-09-08)

`src/hybrid_search/index/claim_split.py` 신설. 순서는 계획대로 고정했다:
코드펜스·셸 라인·이미지 보일러플레이트 제거 → claim 생성 → 게이트.

**1차 측정이 설계 결함을 하나 잡았다.** qa_log가 턴당 26 claim이 나왔고
`list`가 압도적이었는데, 열어 보니 `## Top results`의 **파일 목록**이었다.
그건 주장이 아니라 영수증이다. 구조 파일은 본문 절만 자르도록
`body_for_claims()`를 넣었다(qa_log는 `## Answer excerpt`, memory_card는
Summary/Decisions/Followups, 프론트매터는 제거).

| node_type | claims/청크 중앙값 | p90 | 문자수 중앙값 | 투영 총량 |
|---|---|---|---|---|
| `conv_turn` | **12** | 27 | 45 | 42,995 (3,081 청크) |
| `qa_log` | **9** (수정 전 26) | 26 | 48 | 22,747 (2,013 청크) |
| `memory_card` | 1 | 2 | 109 | 18 (13 청크) |

**판단**: "턴당 5~8개"는 틀렸다 — **9~14개**다. 판단 규칙(중앙값 ≥ 15면
비용 논거 폐기)에는 걸리지 않았지만, 구두점 split 대비 절감은 4배가 아니라
**약 2배**다(conv 84,550 문장 → 42,995 claim). 비용 논거는 **절반만** 살아남았다.

**부수 관찰 두 개**
- `memory_card`가 카드당 claim 1개다. 대부분이 텔레메트리 카드라
  Summary에 내용이 없기 때문이고, 라운드 5에서 잡은 것과 같은 사실이다.
- **품질 게이트는 claim 단위에서 사실상 아무것도 걸러내지 않는다**(0.0~0.4%).
  `is_harness_noise`는 질의를 판정하는 규칙이지 문장을 판정하는 규칙이
  아니다. 심사 #9의 "게이트 제거율"은 따라서 의미 있는 수가 아니고, claim
  단위 잡음은 splitter가 처리해야 한다(지금은 셸·펜스 제거가 그 역할).

### P2 — claim 단위 BM25만 ✅ (2026-09-08) — 갈림길에서 왼쪽

임베딩 없이 스크래치에 임시 tantivy 인덱스를 짓고(**61,599 claim**, 수 초),
질의마다 상위 300 claim → 부모 폴딩(max) → 부모 순위를 쟀다. 비교군은
**같은 조건의 chunk BM25**(같은 질의, 같은 depth, 같은 폴딩 없음)다.

| | Set B (n=41) | Set A (n=20) |
|---|---|---|
| chunk BM25 · found | 0.49 [0.34, 0.64] | 0.70 [0.48, 0.85] |
| **claim BM25 · found** | 0.51 [0.36, 0.66] | **0.90 [0.70, 0.97]** |
| chunk BM25 · top3 | 0.02 [0.00, 0.13] | 0.10 [0.03, 0.30] |
| **claim BM25 · top3** | **0.10 [0.04, 0.23]** | **0.40 [0.22, 0.61]** |
| chunk BM25 · MRR | 0.018 | 0.067 |
| **claim BM25 · MRR** | **0.097** (5.4배) | **0.342** (5.1배) |
| top3 얻음 / 잃음 | 4 / 1 | **6 / 0** |

**판단 규칙 적용**: Set A는 top3 +0.30으로 기준(+0.20)을 넘겼다. Set B는
+0.08로 못 넘겼지만 MRR이 5.4배다(바닥이 낮아서 비율이 큰 것이다).

**결론: 이득의 상당 부분이 어휘적이고 공짜다.** 설계를 임베딩 없이 시작할 수
있다. 46분·346MB는 P3에서 벡터가 추가로 얼마를 주는지 본 뒤에 값을 매긴다.

**읽을 때 주의**: 이 표는 **BM25 레인만** 떼어낸 비교이고 전체 파이프라인
수치가 아니다(벡터·RRF·슬롯 플래너 없음). Set B의 chunk BM25 found 0.49가
end-to-end 0.15보다 높은 것은 depth 300에서 폭넓게 회수했기 때문이다.
설계 판단에는 이 비교가 맞고, 최종 성능 예측에는 쓸 수 없다.

**공정성 확인**: claim BM25는 상위 300 claim이 부모 100~200개로 접히므로
chunk BM25(부모 300개)보다 **더 적은 부모**를 보고도 이겼다.

### P3 — 2단계 풀 + 집계 함수 ✅ (2026-09-09)

claim BM25 상위 N → 부모 폴딩 → 상위 50 부모. depth {100, 300, 1000} ×
집계 {max, top3평균, 길이정규화 max}.

| | Set B (n=41) top3 | Set A (n=20) top3 | 부모/질의 |
|---|---|---|---|
| depth 100 · **max** | **0.10** | **0.40** | 50.0 / 48.6 |
| depth 300 · max | 0.10 | 0.40 | 50.0 / 48.6 |
| depth 1000 · max | 0.10 | 0.40 | 50.0 / 48.6 |
| depth 100 · top3평균 | 0.10 | 0.40 | — |
| depth 300 · top3평균 | 0.10 | 0.25 | — |
| depth 100 · 길이정규화 | 0.05 | 0.20 | — |
| depth 300 · 길이정규화 | 0.00 | 0.15 | — |

**결정 셋**
1. **N = 100.** depth를 10배로 늘려도 `max`의 결과가 한 자리도 안 바뀐다 —
   부모의 최고 claim은 일찍 나온다. 심사가 요구한 2단계는 필요하지만
   깊이는 안 깊어도 된다.
2. **집계는 `max`.** `top3평균`은 depth가 깊어질수록 무너지고(적당한 claim
   3개를 가진 부모가 이긴다), **길이 정규화는 신호를 파괴한다**(Set A
   0.40 → 0.10).
3. **심사 #1(부모 다양성 붕괴)은 해소됐다.** 폴딩 후 부모가 질의당
   50.0 / 48.6개로 목표를 채운다. claim 단위로 50행을 자르면 6~10개가
   된다는 지적은 옳았고, 2단계가 그것을 정확히 막는다.

**심사 #4(max 편향)에 대한 답**: 이론은 맞지만 이 코퍼스에서는 발생하지
않는다. 편향이 성립하려면 어떤 레인이 claim 수에서 유리해야 하는데,
P1 실측은 conv 12 · qa 9 · card 1이다 — 카드가 오히려 가장 적다. 그리고
편향을 직접 교정하는 길이 정규화를 넣어 보니 **더 나빠졌다.**

### P4 — 미스 병인 라벨링 ✅ (2026-09-09) — 가정이 틀렸다

각 미스를 실패 단계로 라벨링했다(`absent` / `pool` / `rank` / `served`).

| | answered | pool 누락 | rank 손실 |
|---|---|---|---|
| Set A (n=20) | 14 | **0** | **6** |
| Set B (n=41) | 6 | **24** | 11 |

**Set A는 회수 문제가 아니다. 전부 순위 문제다.** 심사 #5가 "qa 레인의 같은
병이라는 단정"을 막은 것이 옳았다 — 실제로 다른 병이다.

그리고 그 순위 손실이 구체적이다: C18은 BM25 **1위**인데 융합 후 **101위**,
C7은 3위 → 46위, C20은 3위 → 101위. 한국어 NL의 `bm25_weight=0.15`가
기억 레인에도 그대로 적용돼 어휘 강자를 뭉갠다.

**그래서 가중치를 스윕했고, 답이 아니었다** (end-to-end, 세 축):

| mem_w | A found/top3/MRR | B found/top3/MRR | 코드축 |
|---|---|---|---|
| **0.15** | 0.70 / **0.60** / **0.531** | 0.15 / 0.02 / 0.031 | 0.92 / 0.77 / 0.16 |
| 0.35 | 0.70 / 0.55 / 0.428 | 0.12 / 0.05 / 0.046 | 동일 |
| 0.50 | 0.75 / 0.50 / 0.459 | 0.15 / 0.07 / 0.058 | 동일 |
| 0.70 | 0.75 / 0.50 / 0.476 | 0.12 / 0.05 / 0.062 | 동일 |

Set A의 top3가 떨어지고 Set B가 조금 오른다. 라운드 5가 conv 레인에서 만난
것과 **같은 상충**이다. 결론: **스칼라 하나로는 "확신한 레인을 믿어라"를
표현할 수 없다.** 그것이 claim max 폴딩이 하는 일이고 — 부모마다, 전역
가중치 없이 — 그래서 이 설계가 가중치 조정보다 나은 이유다.

### P5 — 삽입 게이트 ✅ (2026-09-09) — 통과

얼린 스냅샷의 **사본**에 claim을 SQLite + tantivy로 삽입했다(벡터 없음 —
P2/P3에서 이득의 대부분이 어휘적이라 BM25-only가 후보 설계다).
**folding 없이 claim이 필터 없이 경쟁하는 최악 조건**으로 코드 축을 쟀다.


| 코드 축 (n=25) | 삽입 전 | 삽입 후 |
|---|---|---|
| primary-top5 | 0.92 | **0.92** |
| recall@10 | 0.77 | **0.77** |
| memory@3 | 0.16 | **0.16** |
| read_count | 2.40 | **2.40** |

**심사 #6(단일 인덱스 avgdl 오염)은 측정 결과 발생하지 않는다.** 청크 수를
4배로 늘려도 코드 축이 한 자리도 안 움직인다. 게이트 통과.

참고로 같은 증강 인덱스에서 기억 축은 Set A 0.70/0.60/0.538,

- **BM25-only로 시작한다.** 임베딩 46분·346MB는 P2/P3가 요구하지 않았다.
  벡터 claim은 별건으로 값을 매긴다.
- **N=100, 집계 max, 2단계 폴딩(→50 부모).**
- **적용 레인은 conv_turn + qa_log + memory_card.** P4가 Set A의 병을
  다르게 짚었지만, claim 폴딩은 pool이 아니라 **rank**로도 이득을 낸다
  (P2에서 Set A top3 0.10 → 0.40). 그 이득의 근거가 P4로 설명된다.
- **다음 단계는 프로덕션 구현**: 인덱서가 claim 행을 만들고, 융합 후

**남은 미지수**: 이 파일럿은 레인을 떼어낸 비교와 삽입 게이트까지다.
**폴딩을 넣은 end-to-end 수치는 아직 없다** — 그것이 구현 후 첫 측정이고,
기준선은 §8의 P0 표(Set A 0.70/0.60/0.531, Set B 0.15/0.02/0.031)다.

### 10.1 P6a — 구조 splitter는 값을 못 한다

같은 부모에 대해 두 스크래치 BM25 인덱스를 짓고 동일 조건(depth 100 →
부모 폴딩 max → 상위 50 부모)으로 비교했다.

| | 단위 수 | Set B found/top3/MRR | Set A found/top3/MRR |
|---|---|---|---|
| claim (구조 splitter) | 61,599 | 0.37 / 0.10 / 0.096 | 0.65 / **0.40** / 0.340 |
| **sentence (구두점)** | 219,162 | **0.51 / 0.12 / 0.135** | 0.60 / **0.40** / **0.357** |

**Set B에서 문장 분리가 이기고 Set A는 동률이다.** 구조 splitter가 사는 것은
인덱스 크기(3.6배 작음)뿐이고, 검색 품질로는 **아무것도 사지 못한다.**
심사가 예고한 대로다 — 게이트가 0.4%만 거른다는 것은 splitter의 규칙이
거의 발동하지 않는다는 신호였고, 실제로 그 규칙들은 Set B에서 **필요한
문장까지 버리고 있었다**(셸 라인 제거·길이 하한).

### 10.2 P6b — 분해는 Set B를 고치지 않는다. 병을 옮긴다

문항별 교차표(청크 BM25 depth 300 → 문장 분해 후 폴딩 depth 100):

| chunk-level → 분해 후 | Set B (n=41) | Set A (n=20) |
|---|---|---|
| miss → miss | **15** | 5 |
| miss → pooled | 4 | 1 |
| miss → top3 | 2 | 0 |
| pooled → top3 | 3 | **6** |
| pooled → pooled | 11 | 3 |
| **pooled → miss** (회귀) | **5** | 3 |
| **top3 → pooled** (회귀) | 1 | 0 |
| top3 → top3 | 0 | 2 |

**Set A**: `pooled → top3` **6건**이 P4가 라벨링한 rank 손실 **6건과 정확히
일치**한다. 심사 #11이 요구한 문항별 추적이고, 설계의 메커니즘이 이 세트에서
작동한다는 직접 증거다.

**Set B**: 6건을 구하고(`miss→pooled/top3` 6) **6건을 잃는다**
(`pooled→miss` 5 + `top3→pooled` 1). 그리고 **15건은 분해해도 여전히 회수
불가**다. 심사 #4가 옳다 — 분해는 Set B의 pool 문제를 rank 문제로 바꿀 뿐이고,
그 rank를 고칠 메커니즘이 이 설계에 없다.

**miss→miss 15건이 말하는 것**: 이건 입도 문제가 아니다. 질의(패러프레이즈)와
정답 문장이 **어휘를 공유하지 않는다.** 그건 벡터가 하는 일이고, 그래서
"BM25-only로 시작한다"는 §9의 결정은 **Set A에만 유효**하다.

2. **구현 5결정**을 문서로 확정(심사 #10): 기존 청크 중복 검색 · 증분 갱신 ·

3. **폴딩을 넣은 end-to-end**를 P0 기준선(Set A 0.70/0.60/0.531,
   Set B 0.15/0.02/0.031)과 비교. 레인 분리 비교는 설계 판단용이고
   성능 판정용이 아니다.
4. Set B는 **별건으로 분리**한다. 15건의 어휘 불일치는 입도로 안 풀린다.

**목적함수를 먼저 적는다**(심사 #7): 이 시스템의 1차 지표는 **Set A top3**다
(증류된 답을 상위에 올리는 것이 제품의 주장이다). Set B는 하한 제약으로
쓴다 — **Set A top3를 0.60 아래로 떨어뜨리지 않으면서 Set B를 개선**하는
변경만 채택한다.

## 11. 구현 시도와 그 결과 (2026-09-09) — 짓고, 재고, 되돌렸다

§10.3의 정정본대로 지었다. **문장 단위 자식 색인 + 융합 전 부모 폴딩,
증류 레인부터.** 그리고 **되돌렸다.** 무엇을 지었고 왜 안 됐는지 적는다.

### 11.1 지은 것

`SpanIndex` — 기억 레인 부모(qa_log · memory_card · domain_term ·
episodic_example)의 문장을 담는 **별도 tantivy 인덱스**. 설계에서 지킨 것 셋:

- **파생물이다.** 부모 청크에서 언제든 다시 만든다. 잃어도 재구축이지 데이터
  손실이 아니다.
- **분리돼 있다.** 세 저장소의 개수 일치 검사(§12에서 대화 기억을 통째로
  날렸던 그 검사)를 **건드리지 않는다.**
- **선택적이다.** 없거나 깨졌거나 낡았으면 기존 청크 BM25로 그냥 떨어진다.

`index-spans` CLI로 valuein에 **115,471 span / 2,026 청크**를 **1.0초**에
만들었다. 임베딩 0원.

**구현 중 잡은 버그 하나**: 매니페스트를 `meta.json`으로 썼는데 그 이름은
**tantivy 자신의 인덱스 메타파일**이다. 덮어쓰니 인덱스가 안 열리는데,
파생 인덱스는 실패 시 조용히 폴백하도록 만들어 놔서 **아무 에러 없이 그냥
효과가 0이었다.** 옵셔널 설계의 대가다 — 폴백이 버그를 숨긴다.

### 11.2 잰 것 — 안 통한다

얼린 스냅샷, `--repeat 3`, 스프레드 0.00.

| | 기준선 | 대체(span이 chunk BM25를 교체) | 유니온(span 앞, chunk 뒤) |
|---|---|---|---|
| Set A found | 0.70 | 0.70 | 0.70 |
| Set A **top3** | **0.60** | 0.60 | **0.65** |
| Set A MRR | **0.531** | 0.488 | 0.482 |
| Set B found | **0.15** | 0.12 | 0.12 |
| Set B MRR | **0.031** | 0.028 | 0.028 |
| 코드 축 | 0.92/0.77/0.16 | 동일 | 동일 |

유니온이 Set A top3를 한 문항 올리지만 **MRR이 양쪽 다 떨어지고** Set B
found도 한 문항 잃는다. 신뢰구간이 전부 겹친다. **채택 기준(§10.3의
목적함수)을 못 넘는다** — 되돌렸다.

### 11.3 왜 안 통했나 — 메커니즘 둘

레인 단독 측정에서는 크게 이겼다(Set A top3 0.10 → 0.40, P2/P6a). 그게
파이프라인으로 전달되지 않은 이유:

**① 폴딩이 순위 정보를 압축한다.** 부모의 점수는 **가장 좋은 문장 하나**다.
그런데 대부분의 부모가 그럭저럭한 문장 하나쯤은 갖고 있어서, 폴딩된 순위는
청크 순위보다 **평탄해진다.** RRF는 순위를 융합하므로 평탄한 리스트는
기여가 작다. 실제로 대체 방식에서는 이전에 후보였던 부모 4개(C5·C11·C18·C20)가
**상위 100 후보에서 빠졌다.**

**② 기억 헤드는 관련도로 뽑히지 않는다.** `_merge_memory_results`는 후보를
**node_type 우선순위**로 먼저 정렬하고(카드가 qa보다 항상 앞), qa는 **토픽으로
묶어 각 묶음의 최신 것**을 대표로 쓴다. 검색 순위가 아무리 좋아져도 이 두 겹의
필터를 통과하면서 대부분 사라진다.

**진단 증거**: 최종 결과에 못 든 Set A 6문항을 추적하니 C17은 기억 후보
**1위**이자 스플라이스된 헤드 **1위**인데도 최종 결과에 없다. 헤드 이후 단계가
지운다. C7은 후보 32위라 헤드(3칸)에 못 든다. 나머지 4개는 후보에도 없다.

### 11.4 이것이 세 번째다

| 시도 | 레인 단독 | end-to-end |
|---|---|---|
| conv lexical rerank (§14.4) | 이론상 맞음 | 0 |
| 랭킹 규칙 6종 (라운드 3~5) | 일부 유망 | 0 |
| **문장 span 폴딩 (여기)** | **top3 0.10 → 0.40** | **0 또는 음수** |

세 번 다 같은 자리에서 죽었다. **이 파이프라인의 기억 헤드는 관련도로
선택되지 않으므로, 회수·랭킹 쪽 어떤 개선도 거기 닿지 못한다.**

### 11.5 그래서 다음은 회수가 아니라 헤드 선택이다

지금까지 여섯 라운드 동안 고친 것은 전부 "무엇을 회수하고 어떻게 정렬하는가"
였다. 측정이 말하는 다음 대상은 **`_merge_memory_results`의 선택 규칙**이다:

1. **node_type 우선순위가 관련도를 이긴다** — `memory_card`가 점수와 무관하게
   `qa_log`보다 앞선다. 이 규칙이 언제 옳고 언제 틀린지 잰 적이 없다.
2. **토픽 묶음의 대표를 최신으로 뽑는다** — 같은 주제의 옛 답과 새 답이 있을
   때는 옳지만, 묶기가 틀리면 관련도 높은 것을 버린다.
3. **헤드 이후 어떤 단계가 헤드 1위를 지운다**(C17). 무엇인지 특정되지 않았다.

3번이 가장 먼저다 — 버그일 가능성이 있고, 셋 중 유일하게 "설계 결정"이 아니다.

**span 인덱스는 남기지 않았다.** 소비자가 없는 프로덕션 코드는 짐이고,
§14.4에서 conv rerank를 되돌릴 때와 같은 처리다. 무엇을 지었고 왜 뺐는지는
기억 레인 융합 지점의 주석에 남겼다. 헤드 선택이 고쳐지면 그때 다시 짓는다
— 1초짜리 인덱스다.

## 12. 헤드 선택으로 방향을 옮기고 — 버그를 하나 잡았다 (2026-09-09)

§11.5가 지목한 첫 대상("헤드 1위가 최종 결과에서 사라지는 것")을 추적했다.
**설계 결정이 아니라 버그였다.**

### 12.1 추적

Set A의 C17을 단계별로 찍었다. 목표 청크가 어디까지 살아 있는지:

```
after _merge_memory_results   11행 중 1위
after _merge_conv_results     14행 중 1위
after _order_qa_by_recency    14행 중 1위
after _interleave_modules     10행 중 1위
before supersession           10행 중 1위
after supersession            없음        ← 여기
FINAL                         없음
```

### 12.2 원인 — 통합 노트가 통합 노트를 대체한다

`qa_supersession`에 이런 행이 있었다:

```
stale : .hybrid-search/qa/consolidated/2026-09-04-ba961239.md   ("머지·푸시했어?")
newer : .hybrid-search/qa/consolidated/2026-09-04-3faa182b.md   ("메인에 푸시했어?")
```

**둘 다 Reflector 통합 노트다.** 서로 다른 클러스터를 정리한 **별개의 답**인데,
같은 날 같은 영역(git·배포)에 대해 여러 노트가 쓰였고 토픽 매처가 둘을 묶었으며,
타임스탬프가 나중인 쪽이 앞의 것을 "낡았다"고 판정했다.

그리고 그 판정이 파괴적이다. `_splice_superseding`은 **정원이 찼을 때
낡은 항목을 교체**한다(코드 항목이 스플라이스에 자리를 뺏기지 않게 하려는
설계다). `limit=10`에 결과가 10행이면 원본이 그대로 **빠진다** — 질문에
답하던 그 노트가.

규모는 작다: valuein 601행 중 **2행**, 이 레포는 39행 중 0행. 그런데 그
2행이 Reflector 노트를 결과에서 지우고, Set A가 그 노트들로 만들어졌다.

### 12.3 수정 — 양쪽에

**상류**(`compute_supersession`): 통합 노트는 supersession의 **낡은 쪽이
될 수 없다.** 통합물은 자기 클러스터의 종합이지 다른 종합의 옛 버전이 아니다.
노트가 자기 원본 로그를 대체하는 방향은 **설계 그대로 유지**된다.

**검색 단**(`_splice_superseding`): 2026-09-09 이전에 만들어진 인덱스에는
그런 행이 이미 들어 있다. 그것을 실행하면 여전히 노트가 지워지므로, 저장된
매핑이라도 낡은 쪽이 통합 노트면 **작동하지 않는다.** 이 절반이 없으면
수정이 재인덱싱을 기다려야 한다.

라운드 5의 텔레메트리 카드와 같은 짝이다 — 상류는 새로 생기는 것을 막고,
검색 단은 이미 있는 것을 막는다.

### 12.4 실측 — 이번엔 통한다

| | 기준선 | 수정 후 |
|---|---|---|
| Set A answer_found | 0.70 [0.48, 0.85] | **0.75 [0.53, 0.89]** |
| Set A **answer_in_top3** | 0.60 [0.39, 0.78] | **0.65 [0.43, 0.82]** |
| Set A MRR | 0.531 | **0.581** |
| Set B | 0.15 / 0.02 / 0.031 | **동일** |
| 코드 축 | 0.92 / 0.77 / 0.16 | **동일** |

세 지표가 함께 오르고 아무것도 안 내려간다. 신뢰구간은 여전히 겹치지만
(n=20의 한계), **두 문항이 문항 단위로 설명된다**는 점이 다르다 — 이 세션
내내 실패한 튜닝들과 달리 이건 잘못된 동작을 없앤 것이다.

테스트 6건 추가(상류 3 · 검색 단 3), 전체 **1,744 통과**.

### 12.5 이 라운드가 남긴 방향

§11.4의 표에 한 줄이 더 붙는다 — 그런데 이번엔 반대쪽이다.

| 시도 | 레인 단독 | end-to-end |
|---|---|---|
| conv lexical rerank | 이론상 맞음 | 0 |
| 랭킹 규칙 6종 | 일부 유망 | 0 |
| 문장 span 폴딩 | top3 0.10 → 0.40 | 0 또는 음수 |
| **supersession 버그 수정** | — | **+0.05 top3 · +0.05 MRR** |

**회수·랭킹을 네 번 고쳐서 0이었고, 결과 선택 단계의 버그 하나를 고쳐서
움직였다.** §11.5의 진단이 맞았다.

남은 두 개도 같은 자리에 있다:
1. **node_type 우선순위가 관련도를 이긴다** — `memory_card`가 점수와 무관하게
   `qa_log`보다 앞선다. 언제 옳고 언제 틀린지 잰 적이 없다.
2. **토픽 묶음의 대표를 최신으로 뽑는다** — 묶기가 틀리면 관련도 높은 것을
   버린다. supersession과 같은 매처를 쓰므로 같은 종류의 오류가 있을 수 있다.
