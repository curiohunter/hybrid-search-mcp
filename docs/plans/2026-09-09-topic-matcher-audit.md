# 주제 매처 감사 — 한국어 쪽에 불용어 바닥이 없었다

**작성** 2026-09-09 · **상태** 구현·측정 완료 · **선행** `docs/handoff/2026-09-09-memory-head-selection.md` §1

---

## §1. 왜 이걸 봤나

앞 세션의 성과 두 개(`9ad7c97` supersession 버그, `e8d8a2b` 대표 규칙)가
**둘 다 매처를 고친 게 아니라 매처 결과에 덜 의존하게 만든 것**이었다.
인계 문서가 지목한 다음 대상이 매처 자신이다. 첫 걸음도 거기 적혀 있었다 —
"통합 노트 20건 전조합에 매처를 돌려 같은 주제로 판정되는 쌍을 전부 뽑고,
§12의 쌍이 유일한 오탐인지 빙산의 일각인지 가른다."

**답: 빙산의 일각이었다.**

---

## §2. 전조합 감사 결과

20건 × 190쌍. 같은 주제로 판정된 쌍 **15개**, 그중 6개는 인덱스 시점의
엄격한 술어(`_same_topic_strict`)까지 통과했다.

그런데 15쌍이 고르게 흩어져 있지 않았다. **전부 한 덩어리에서 나왔다** —
노트 7건이 완전 연결에 가까운 클리크를 이루고, 나머지 13건은 어떤 쌍도
만들지 않았다.

그 7건은 전부 git 작업 지시 턴에서 증류된 노트였고, 제목을 보면 **서로 다른
일곱 개의 사실**이다: 푸시 전 사전 확인 / 실물로 답하기 / 푸시 상태 점검이
잡아내는 실수 / 머지→빌드→푸시→배포 순서 / 워크트리 삭제 전 미머지 확인 /
푸시와 배포의 분리 / "모두"의 범위 되묻기. 서로를 대체하는 버전이 아니라
서로를 보완하는 규칙들이다. supersession이 "새 것이 낡은 것을 대체한다"고
말할 수 있는 관계가 아니다.

## §3. 무엇이 그것들을 묶고 있었나

쌍마다 공유 가중치를 실어 나른 토큰을 세어 봤다. 상위 20개 중 **8개가
한국어 기능어**였다 — 것이, 다른, 아니, 실제, 있다, 먼저, 같은, 된다.
모두 가중치 1.0, 즉 **distinctive(변별적) 토큰으로 계산되고 있었다.**

원인은 모듈 자신의 이력에 있다. 2026-07-13에 영어 쪽 구멍(스테머 없음)을
막으면서 영어에는 불용어 80개와 저정보 단어 60개를 줬는데, **한국어에는
그 대응물을 주지 않았다.** 한국어가 받은 것은 의문사 24개(`_KO_INSTRUCTION`)와
도메인 명사 10개(`_KO_GENERIC_PREFIXES`)뿐이다. 계사·지시사·수량사와
하다/되다/있다/없다 활용형이 전부 만점 가중치로 흘러 다녔다.

**왜 골드셋이 못 잡았나 — 이게 핵심이다.** 이 오염은 **길이에 비례한다.**
골드셋의 답변은 전부 한 문장이라 기능어가 쌓일 자리가 없다. 실제 통합
노트는 1.5k자다. 같은 쌍을 짧은 답변으로 쓰면 안 뭉치고, 실제 길이로 쓰면
뭉친다 — 합성 데이터로 양쪽 다 재서 확인했다.

| 합성 쌍 KO-A13 (인접, 반드시 분리돼야 함) | answer_overlap | 묶임? |
|---|---|---|
| 짧은 답변(한 문장) | 0.28 | 아니오 |
| 실제 노트 길이 | 0.35 | **예 (오탐)** |

## §4. 수정

`_KO_STOPWORD_PREFIXES` — `_EN_STOPWORDS`의 한국어 대응물. 2글자 접두 형태로
비교되므로 접두 형태로 등재하고, **드롭**한다(0.3 감쇠가 아니라).

구성 원칙 세 가지:

1. **닫힌 부류만.** 문서빈도를 2,240건의 실제 qa 노트에서 뽑아 후보를 만들되,
   고빈도라도 **도메인 명사는 넣지 않는다.** 한 코퍼스에 과적합된다.
   (실제로 DF 55%짜리 도메인 명사가 후보에 올라왔고 뺐다.)
2. **접두 충돌은 제외.** 2글자 접두는 기능어와 주제어를 구별하지 못한다.
   그래(그래프), 그리(그리드), 이미(이미지), 자기(자기오염) — 넷은 고빈도
   기능어지만 **일부러 목록에 없다.** 단위 테스트가 이 넷을 지킨다.
3. **저정보 용언·명사는 드롭이 아니라 0.3.** 만들/생성/적용/진행/상태/결과…
   영어 쪽 `_EN_GENERIC_WORDS`와 같은 취급이다.

## §5. 측정

### 5.1 술어 수준 — 정밀도 45% 개선

무작위 20만 쌍에 인덱스 시점 술어를 돌린 수용률:

| | 수용 / 10k쌍 |
|---|---|
| 수정 전 | 19.2 |
| 수정 후 | **10.6** |

수용된 쌍을 표본으로 눈으로 보면 차이가 분명하다. 수정 전에는 긴 서술 턴이
그와 아무 상관 없는 짧은 일반 지시 턴에 붙는 유형이 다수 섞여 있고, 수정 후
남은 것은 대체로 같은 요청이 반복된 경우다. (원문 발화는 여기 옮기지 않는다 —
`CLAUDE.md`. 표본은 재는 쪽에서 확인할 것.)

**저장된 supersession 매핑**(valuein): 604 → **502**. 본 레포는 43 → 48로
**늘었다** — 노이즈를 양쪽에서 빼면 분모도 줄기 때문에, 진짜 같은 주제인 쌍은
비율이 **올라간다.** 임계값을 올리는 것과 다른 점이 이것이다.

### 5.2 골드셋 — 무회귀, 그리고 새 게이트

기존 84쌍 전 슬라이스 동일(ko/en/mixed × same/adjacent/bridge, gate PASS).
`same` 슬라이스 재현율이 그대로라는 게 중요하다 — 정밀도만 올렸다.

여기에 **긴 답변 슬라이스 4쌍**을 추가했다(KO-A13/A15, KO-S13/S14). 이 4쌍은
합성이고, 실제 코퍼스를 인용하지 않는다(`CLAUDE.md`). 검증:

- 구 매처: `GATE FAIL — ko/adjacent 13/14, false group (KO-A13)`
- 신 매처: `gate: PASS`

즉 **실제로 회귀를 잡는 게이트**다. 골드셋이 못 보던 실패 유형을 이제 본다.

### 5.3 End-to-end 3축 — 전부 평평

얼린 스냅샷, `--repeat 3`, 스프레드 0.00.

| | 수정 전 | 수정 후 |
|---|---|---|
| Set A answer_found | 0.75 | 0.75 |
| Set A **answer_in_top3** | **0.70** | **0.70** |
| Set A MRR | 0.571 | 0.571 |
| Set B found / top3 | 0.02 / 0.02 | 0.02 / 0.02 |
| 코드축 primary-top5 / recall@10 / memory@3 | 0.92 / 0.77 / 0.16 | 0.92 / 0.77 / 0.16 |

Set A는 **질의별로도 20/20 전부 무변화**. Set B는 4행이 memory_hits 개수만
±1 움직이고 순위·정답 여부는 그대로다.

**이걸 어떻게 읽어야 하나.** 인계 문서의 지뢰 #1("레인 단독 측정은 파이프라인을
예측하지 못한다")이 다섯 번째로 확인된 것처럼 보이지만, 성격이 다르다.
앞의 네 번은 *점수를 올리려는* 변경이 0을 냈다. 이번 것은 *파괴적 동작을 막는*
변경이고, 목적함수의 제약(Set A top3 ≥ 0.70)을 지킨 채 정밀도를 45% 올렸다.
골드셋 20문항이 사라진 **209건의 잘못된 대체**를 하나도 밟지 않았다는 뜻이지,
209건이 잘못되지 않았다는 뜻이 아니다. (같은 패스에서 107건이 새로 생기고
136건이 대상을 바꾼다 — 완전 연결 묶음이라 멤버가 재배치되기 때문이고,
그래서 매핑 **개수**는 정밀도의 대리 지표가 못 된다. §5.1의 술어 수용률이
그 자리를 대신한다.)

**채택 근거**: 3축 무회귀 + 술어 정밀도 45% + 골드셋 재현율 불변 + 새 게이트.

### 5.4 목록을 완성하려다 되돌린 것

부끄러운 비대칭이 하나 남아 있다: `합니`·`입니`·`있습`은 목록에 있는데
`했습`·`없습`·`됐습`은 없다. 오탈이 아니라 **측정이 멈추라고 한 지점**이다.

패러다임을 완성하고(했습/없습/됐습/하겠/되어/이었/있음/있던/있을/같습)
지시·의문사(이게/그건/이제/어떻/어느/무엇)까지 넣어 구현한 뒤 쟀다:

| | 술어 수용/10k | Set A top3 | Set A MRR |
|---|---|---|---|
| 채택안 (현재) | 10.6 | 0.70 | **0.571** |
| 활용형까지 확장 | 10.1 | 0.70 | 0.546 |
| 지시·의문사까지 확장 | 10.1 | 0.70 | 0.546 |
| 저정보 명사까지 추가 | 10.1 | 0.70 | 0.546 |

손실은 전부 한 질의다(C6, 1위 → 2위). 세 확장 각각이 **독립적으로** 그 순위를
깎았고, 대가로 얻은 정밀도는 10.6 → 10.1로 미미하다. **측정된 비용이 있고
측정된 이득이 없는 변경은 싣지 않는다.** 되돌린 뒤 Set A가 0.571로 정확히
복귀하는 것까지 확인했다(결정성 검증).

이 판단은 코드 주석과 `test_list_is_not_extended_past_what_measurement_supports`에
박아 뒀다. 다음 사람이 "빠진 활용형"을 무심코 채우지 않도록.

## §6. 남은 것

### 6.1 매처 소비자는 셋이 아니라 넷

인계 문서는 세 곳을 적었다(`supersession._same_topic_strict`,
`orchestrator._qa_topic_groups`, `_order_qa_by_recency`). **네 번째가 있다** —
`memory/reflector.py`가 클러스터링에 같은 엄격 술어를 쓴다. 즉 이번 변경은
앞으로의 Reflector 묶음도 더 좁게 만든다. 수동 트리거라 이번엔 측정하지
않았다. 다음 Reflector 실행 때 클러스터 크기를 기록해 둘 것.

### 6.2 남은 6쌍은 오탐이 아니다

수정 후에도 통합 노트 7건 중 6쌍이 엄격 술어를 통과한다. 그런데 그 6쌍은
질문 문자열이 사실상 같은 요청의 다른 표현이다(같은 작업을 묻는 어미만 다른 턴).
매처가 같은 주제라고 보는 건 **맞다.** 문제는 그 위에 있다 — Reflector가
사실상 같은 반복 질문을 3개의 노트로 증류했고, 헤드 선택이 그중 하나만
노출한다. **이건 매처가 아니라 Reflector 클러스터링 문제다.**

### 6.3 경계 사례 하나를 골드셋에 넣지 않았다

`KO-A14`(머지→배포 순서 ↔ 푸시 전 확인 항목)는 수정 후에도 묶인다.
질문 경로 0.33 / 답변 경로 0.23으로 양쪽 임계값을 아슬하게 넘는다.
이걸 adjacent로 못 박으려면 **절차 어휘**(머지/푸시/배포/커밋/브랜치)를
저정보로 내려야 하는데, 그러면 절차 자체를 묻는 질문이 안 묶인다.
방어할 자신이 없는 판단이라 골드셋에 넣지 않았다. 다음에 다룬다면
임계값이 아니라 **최소 절대 공유 질량**(비율만으로는 증거가 안 된다) 쪽을
볼 것 — 짧은 명령형 턴 문제와 뿌리가 같다.

## §7. 재현

```bash
python benchmarks/topic_gold_eval.py          # 게이트
python -m pytest tests/test_qa_topics.py -q   # 구조 계약

# 전조합 감사 — 노트 디렉토리의 모든 쌍에 두 술어를 돌려 묶이는 쌍을 뽑는다
python benchmarks/topic_pairs_audit.py --dir <프로젝트>/.hybrid-search/qa/consolidated

# 술어 수용률 — 정밀도 대리 지표 (매핑 개수 말고 이걸 볼 것)
python benchmarks/topic_predicate_rate.py --config $SNAP/config.toml \
  --project <이름> --pairs 200000

# 얼린 스냅샷에 매처 변경을 반영 (임베딩 없음, 순수 CPU)
python benchmarks/recompute_supersession.py --config $SNAP/config.toml
```

3축 측정은 인계 문서 §"측정 규약" 그대로. 단 **supersession 매핑은 인덱스
시점에 저장되므로**, 매처를 고친 뒤 얼린 스냅샷을 재려면 스냅샷 안에서
`compute_supersession`을 다시 돌려 넣어야 한다. 임베딩이 아니라 순수 CPU라
재인덱싱 비용은 들지 않는다. 이걸 빼먹으면 매처 변경이 측정에 **보이지
않는다** — 구 매처로도 한 번 재계산해 기준선이 안 움직이는 것부터 확인할 것
(실제로 604 → 604로 동일했다).
