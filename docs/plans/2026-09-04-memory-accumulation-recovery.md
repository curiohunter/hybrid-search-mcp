## 2. 실행 순서와 측정 설계

```
P0  Reflector 1회        (즉시, 코드 변경 0)
P1  selfeval v1.1        (계측기 + 골드셋 공급)
P2  conv 백필 + 재캘리브레이션  (사전 게이트 → 리플레이 → 백필 → 리플레이 → recalibrate)
```

**왜 백필이 마지막인가.** 백필은 valuein 코퍼스를 +32.5% 늘린다(§3 P2-2).
P1을 먼저 넣으면 선주입 레인이 채점되기 시작하고, **P1이 정규화한 harvested가
P2 리플레이셋과 recalibrate 골드셋의 보강분**이 된다. 2분짜리 작업을 먼저
하고 싶은 유혹이 있지만, 측정 없는 코퍼스 확대는 자기오염 감사(2026-07-09)에서
이미 한 번 대가를 치른 실수다.

**측정은 시간창 A/B가 아니라 고정 리플레이셋.** 라이브 트래픽의 전후 기간
비교는 질문 자체가 달라져 교란된다. 동일 쿼리 집합을 백필 **직전·직후**에
리플레이해 결정론적으로 비교한다.

- 리플레이셋: `benchmarks/valuein_gold.json` (**25문항**, v1 스키마,
  `project_path` 기준 상대경로 gold) + P1이 정규화한 harvested 유효분
- 러너: **기존 도구를 쓴다** — `benchmarks/run_valuein_bench.py`
- 지표: 러너가 이미 출력하는 **`recall@10`** 을 주지표로,
  `primary_top5` · `memory@3` · grep 베이스라인을 보조로 본다.
  "gold 중 **하나 이상**이 top-10에 들면 성공"이 recall 정의다.
- 백필된 과거 대화를 사후 채점하지는 **않는다** — 그건 다른 자다.

### P1 — selfeval v1.1: 선주입 레인 채점

**목표.** `trigger: user_prompt_submit`으로 주입된 결과의 채택 여부를
채점해 채점 대상을 넓힌다.

#### P1-1. 기존 채점기 재사용 가능성 — 코드로 확인 완료

심사 지적: "`score_event()`는 도구 호출 트랜스크립트를 전제하므로 선주입에
그대로 못 쓴다."

**확인 결과 재사용 가능하다.** `score_event(event: dict)`의 입력 계약은
평범한 딕셔너리 `{"query", "paths", "reads", "greps"}`이며
(`selfeval.py:154-180`), `tool_use` / `tool_result` 블록에 대한 의존은
**전적으로 `extract_turn_events()` 쪽에만** 있다(l.124-137). 채점 로직
자체(순위 매칭 → adopted/mixed/betrayed/no_followup)는 증거의 출처를
가리지 않는다.

따라서 필요한 것은 **추출기 하나**지 새 채점 모듈이 아니다:

```python
def extract_prefetch_event(turn_records: list[dict], pending: dict) -> dict:
    """선주입 1건 = 턴 전체의 Read/Grep을 증거로 삼는다.

    도구 호출 레인은 '검색 호출 이후 ~ 다음 검색 전'으로 followup을 귀속하지만,
    선주입은 턴 시작 시점에 1회뿐이므로 턴 전체가 귀속 구간이다.
    """
    return {"query": pending["query"], "paths": pending["top_paths"],
            "reads": <턴 전체 Read file_path>, "greps": <턴 전체 Grep pattern>}
```

#### P1-2. pending 사이드카 — 결정론적 키와 세션 격리

심사 지적(타당): 프롬프트 문자열을 소비 키로 쓰면 같은 질문 반복·동시 세션에서
비결정적이고, 매칭 실패가 24h 뒤 조용히 사라진다.

- **저장 위치**: 단일 파일이 아니라 **세션별**
  `.hybrid-search/selfeval/pending/<session_id>.jsonl` — 동시 세션 경합 제거
- **레코드**: `{qa_record_id, session_id, ts, query, top_paths[:10], source:"prefetch"}`
  — 소비 키는 **`qa_record_id`**, 프롬프트 문자열이 아니다
- **`qa_record_id`는 새로 만들 필요가 없다 (확인 완료)**:
  `qa_log.record()`의 시그니처가 `-> Path | None`이고, `async_write=False`일 때
  **기록한 파일 경로를 반환**한다(`qa_log.py:361-378`). 선주입 훅은 이미
  `async_write=False`로 호출하므로(`hooks.py:433`, "Sync write — hook lifecycle
  is already synchronous") 반환 경로를 그 자리에서 받는다.
  **`qa_record_id` = 그 Path의 stem** (`01-074413-662a5e0c` 꼴;
  뒤 8자리는 `sha256(query)[:8]`, l.143). 파일명이 곧 결정론적 식별자다.
- **쓰기**: `hooks.py:433`의 `qa_log.record()` 반환값을 받아 즉시 append
  (현재는 반환값을 버리고 있다 — 이 한 줄이 P1의 최소 변경점이다)
- **소비**: `hooks.py:559` Stop 훅에서 자기 `session_id` 파일만 열어 해당
  턴의 `qa_record_id`를 소비 후 삭제. 다른 세션 파일은 건드리지 않는다
- **누락 가시화**: 소비 실패·고아 pending은 조용히 넘기지 말고
  `.hybrid-search/selfeval/misses.jsonl`에 사유와 함께 기록. 24h 초과분 정리
- 훅 컨텍스트 규약대로 전 구간 예외 무해화(세션을 절대 깨지 않는다)

> **사이드카를 남기는 이유.** 일회성 마이그레이션 파서는 깨져도 재실행하면
> 되지만, 훅 핫패스가 md 포맷에 결합되면 포맷을 바꿀 때마다 조용히 채점이
> 멈춘다. 이중 쓰기는 **임시 구조**임을 명시한다 — `qa_log.record()`가
> 구조화 레코드를 단일 소스로 내보내고 md가 그 파생물이 되도록 통합하는 것이
> 다음 정본화 과제다(별건, §5).

> 태깅만으로 어휘적으로는 0건이 되어, 유효 골드가 0개여도 통과해 버린다.
> 실질 기준(유효 ≥3)으로 바꾼다. 유효분이 3 미만이면 P1-3 소급 채점이 새로
> 수확한 harvested로 보강한다 — 294건 모집단이 있으므로 보강은 가능하다.

| 유효 골드 경로 | ≥3 | **29** (valuein) |
| 표준출력 계약 | 준수 | `parsed_md=248 matched_turns=156 scored=156` |
| 신규 테스트 | 통과 | 15건 |

**계획에 없던 수정 — 채점기가 이 코드베이스의 지배적 도구를 못 보고 있었다.**
1차 소급 결과가 `adopted=0 / betrayed=17 / no_followup=139`로 나왔다. 원인을
파고드니 계측 결함이었다: `score_event`의 증거는 **Read와 Grep뿐**인데,
valuein의 실제 도구 분포는 `Bash 1972 · Edit 579 · Read 260 · Grep 0`이다.

- 선주입이 준 파일을 **Edit**하면 채택인데 `no_followup`으로 찍혔다.
- `rg`/`grep`을 **Bash로** 치면 배신인데 역시 `no_followup`으로 찍혔다.
  (Grep 도구는 이 프로젝트에서 2,906턴 중 **0회** 쓰인다.)

그래서 증거를 넓혔다 — 채택은 `Read/Edit/Write/NotebookEdit`, 배신은
`Grep` + `rg|grep|ag|ack|find|fd`로 시작하는 Bash(`&&`/`;` 각 세그먼트 검사,
파이프 뒤 grep은 출력 필터링이므로 제외). 재채점 결과:

| | 1차 (Read/Grep만) | 재채점 (증거 확장) |
|---|---|---|
| betrayed | 17 | **55** |
| no_followup | 139 | **100** |
| harvested | 22 | **45** (유효 골드 29) |

`--retro-reset`은 이 재채점을 위해 추가했다. 소급 행은 qa 로그+트랜스크립트에서
언제든 재도출되는 파생 데이터이므로, 채점기가 바뀌면 두 세대를 한 파일에
섞어 두는 대신 다시 만든다.

**P1이 드러낸 실측 — 선주입은 거의 채택되지 않는다.** 156건 중
adopted 1 · betrayed 55 · no_followup 100. 서빙된 상위 경로 754개의 구성은
실제 파일 48% · qa 로그 44% · 대화 청크 6%로, **가상 경로(열 수 없는 것)가
절반**이라는 점이 일부를 설명한다. 그러나 나머지 절반이 실제 파일인데도
채택이 1건이라는 사실은 설명되지 않는다. 이것은 이번 계획의 수정 대상이
아니라 **계측기가 처음으로 보여준 숫자**이며, 다음 라운드의 입력이다
(참고: 리트리벌 병목은 랭킹이 아니라 노출이라는 기존 조사와 방향이 같다).

### P2 — conv 백필 + 재캘리브레이션

**P2-1 end-to-end 실측 — 계획의 추정이 틀렸다.** §0 정정 A는 "스캔 24초 +
임베딩 1.4분 = 2분 미만"이라고 합성 추정했다. 본 레포 실측은
**308 청크에 2분 57초**다. 라운드1 심사가 "합성 합계는 end-to-end가 아니다"라고
지적한 것이 맞았다 — DB 쓰기·BM25 커밋·벡터 저장·Codex 스캔이 지배적이고,
임베딩은 원격 호출이라 CPU가 아니라 대기가 시간을 먹는다. 요금은 여전히 0원.

또한 본 레포 백필이 **19 세션 / 308 청크**로 나왔다 — 계획의 "3 세션 / 140
청크" 추정은 Claude 트랜스크립트만 센 값이고, 실제로는 cwd가 일치하는
**Codex 세션**이 함께 들어온다.

**P2-2 사전 게이트 — 명령 자체에 넣었다.** 일회성 스크립트 대신
`index-conversations`에 `--max-memory-ratio`(기본 0.40)를 붙였다.
`collect_project_chunks()`가 DB에 아무것도 쓰지 않으므로 **쓰기 전에** 비율을
계산하고, 초과하면 실행하지 않는다. 본 레포 실측:
`chunks 3842 → 4150 (+308) · memory 256 → 564 (13.6%, limit 40%) · PASS`.

게이트 구현 중 결함 하나를 잡았다: 인덱스가 비어 있는 프로젝트는 어떤 conv
청크든 100%가 되어 **자기 첫 임포트를 스스로 막는다**. 희석할 코퍼스가 없을
때는 게이트를 건너뛰도록 고치고 테스트로 고정했다(`total == 0` → SKIP).

**P2-3 리플레이(전) 기준선** — `run_valuein_bench.py`, gold 25문항:

**P2-6 정리 — 실행하지 않기로 바꿨다.** 계획은

그 문제는 이미 없다(qa_log 청크 0). 남은 것은 정상적인 워크트리 코드 인덱스의

### 운영 사고 하나 — 임베딩 백엔드를 동시에 두 번 때리지 말 것

인덱서가 **무한 대기**에 빠져 20분간 멈췄고 인덱스가 절반 상태로 남았다.
멈춘 프로세스를 죽이자 ollama가 **즉시 회복**했다 — 우리 쪽 죽은 연결이 원인이었다.
락은 stale로 남아 재실행도 막았다.

교훈 둘: ① **한 임베딩 백엔드에 벌크 작업을 동시에 걸지 않는다.**
② **벌크 임베딩 경로에 타임아웃이 없다** — 선주입에는
`HYBRID_SEARCH_EMBED_DEADLINE`이 있는데 인덱싱 경로에는 없어서 영원히 기다린다.
다음 라운드 과제.

### 라운드 2 검증 중 발견 — reindex 한 번이 대화 기억을 통째로 지운다

라운드 2를 마치고 valuein에 `reindex`를 돌렸더니 **conv_turn 3,029 → 0**이 됐다.
계획 전체가 되살리려던 그 데이터다. 로그 첫 줄이 원인을 그대로 말한다:

```
Consistency mismatch: SQLite=17881, Tantivy=16457, USearch=16457.
Triggering atomic rebuild.
```

**연쇄는 이렇다.**

1. 앞서 동시 실행으로 물린 conv 인덱서를 죽였다. `_index_session`은 세션마다
   SQLite에 쓰고 `file_hash`를 확정하지만 **BM25 커밋과 벡터 저장은 전 세션이
   끝난 뒤 한 번**이다. 그래서 중간에 죽으면 SQLite는 "이 세션 끝났다"고
   말하는데 검색 엔진엔 그 청크가 없다.
2. 재개 실행은 그 45개 세션을 `unchanged`로 건너뛰었다(해시가 맞으니까).
   드리프트 1,424청크가 그대로 남았다.
3. `reindex`가 드리프트를 감지하고 **원자적 재구축**을 걸었다.
4. `_rebuild_project_atomically`는 새 디렉토리에 **디스크에서만** 인덱스를 짓고
   스왑한다. 대화 청크는 `.conversations/<source>/<session>.jsonl`이라는
   **디스크에 없는 가상 경로**라 재구축 대상이 아니다 → 스왑과 함께 소멸.

**왜 커밋은 살아남았나.** reindex 꼬리가 커밋 인덱서를 무조건 다시 돌린다
(`Commits indexed: +4`). 커밋에는 되살릴 주체가 있고 **대화에는 없었다.**
스캐너가 `_VIRTUAL_PATH_PREFIXES`로 삭제 감지에서 애써 보호하는 바로 그
네임스페이스를, 재구축 경로가 뒷문으로 날리고 있었다.

**수정.** `IndexingResult.conversations_dropped` — 재구축이 스왑 **전에** 옛
인덱스의 대화 세션 수를 세어 기록하고, `cmd_reindex`가 0이 아니면
트랜스크립트에서 다시 만든다. 커밋과 같은 대칭이 된다. 인덱서가 델타 기반이라
잃지 않은 경우엔 no-op이다.

**남은 상류 결함(다음 라운드).** 벌크 conv 인덱싱이 **세션마다 커밋하지 않는다.**
`_index_session`의 크래시 안전 주석("a crash leaves file_hash='' → re-indexed
next run")은 세션 중간 크래시만 막고, **전역 커밋 전 크래시**는 못 막는다.
세션 단위로 BM25/벡터를 커밋하거나, 커밋되지 않은 세션의 해시를 확정하지 않아야
한다. 여기에 §11의 "벌크 임베딩 경로에 타임아웃이 없다"가 겹치면
"멈춤 → 강제 종료 → 드리프트 → 재구축 → 기억 소멸"이 한 줄로 이어진다.

## 12. 연쇄를 끊는다 (2026-09-05)

§11이 남긴 것은 마지막 고리 하나만 막은 상태였다. 연쇄 전체는 이렇다:

```
① 임베딩 요청이 무한정 길어진다
   → ② 손으로 죽인다
      → ③ SQLite는 "끝났다"는데 검색 엔진엔 없다 (드리프트)
         → ④ 드리프트를 손상으로 읽고 전체 재구축
            → ⑤ 재구축은 디스크에서만 지어 대화 기억이 소멸
```

§11에서 ⑤만 고쳤다. 나머지 넷을 고친다.

### ① 임베딩 요청에 전체 상한이 없었다

**진단 정정.** "타임아웃이 없다"고 적었는데 틀렸다 — `urlopen(timeout=120)`은
있었다. 문제는 그것이 **소켓 작업당** 상한이지 요청 전체의 상한이 아니라는
것이다. 반쯤 살아 있는 엔드포인트는 그 안에서 얼마든지 오래 붙잡을 수 있다.
게다가 `TimeoutError`는 `URLError`가 아니라 **어느 except에도 안 걸려서**,
터질 때 `http.client` 깊은 곳의 `TimeoutError: timed out`으로만 나온다 —
로그만 보고는 임베더가 원인인지 알 수 없다.

- `_BULK_EMBED_DEADLINE = 300초`. 선주입 훅만 갖고 있던 데드라인을
  **모든 호출의 기본값**으로 돌렸다. 벌크 작업은 느려도 되지만 무한하면 안 된다.
  `HYBRID_SEARCH_EMBED_DEADLINE=0`으로 끌 수 있다.
- `TimeoutError`를 잡아 임베더 이름·경과 시간·추정 원인이 담긴
  `ConnectionError`로 바꾼다. 실패가 **읽히는 형태**여야 다음 사람이 안 헤맨다.

### ③ SQLite가 검색 엔진보다 먼저 "끝났다"고 말했다

**진짜 원인.** `_index_session`이 청크와 **같은 트랜잭션에서** 최종
`file_hash`를 썼다. BM25 커밋과 벡터 저장은 전 세션이 끝난 뒤 한 번뿐인데,
SQLite는 세션마다 "이건 끝났다"고 커밋한 것이다. 코드 주석은
"크래시가 나면 file_hash=''가 남아 다음 실행에 재인덱싱된다"고 주장했지만,
그 확정이 같은 트랜잭션 안에 있어 **세션 중간 크래시만** 막았다.

- **순서를 뒤집었다.** `_index_session`은 이제 해시를 쓰지 않고
  `_SessionWrite`를 돌려준다. `_checkpoint`가 **BM25 커밋 → 벡터 저장 →
  그 다음에** 해시들을 한 트랜잭션으로 찍는다. 먼저 찍으면 데이터를 잃고,
  나중에 찍으면 최대 한 체크포인트만큼 다시 하면 된다.
- 체크포인트는 500청크 또는 25세션마다. 실측 57 chunks/s 기준 재작업 10초 이내.
- **미확정 세션은 통째로 다시 만든다.** 해시가 빈 세션은 SQLite에 행이 있으므로
  id 델타로는 `to_add`가 비어 영원히 엔진에 안 들어간다. 그 경우 기존 청크를
  지우고 전부 다시 넣는다(양쪽 삭제 경로 모두 모르는 id에 관용적임을 확인).

### ④ 복구 가능한 상태를 손상으로 읽었다

크래시 직후엔 여전히 SQLite가 앞선다(청크는 있고 엔진엔 없다). 그런데 그건
**해당 인덱서가 다음 실행에 스스로 고치는 상태**지 손상이 아니다.
일관성 검사가 그걸 구분하지 못해 재구축을 불렀다.

- `StoreDB.count_unfinished_chunks()` — 빈 해시 파일에 속한 청크 수.
- 검사는 `chunk_count - unfinished`를 엔진 수와 비교한다. 즉 **아직 정착하지
  않기로 되어 있는 것은 세지 않는다.**

### 남은 위험과 그 성질

세 저장소에 걸친 완전한 원자성은 2PC 없이는 불가능하다. 남는 경우는
**엔진이 앞서는 쪽**(체크포인트 직후 SQLite 쓰기 전에 죽는 경우)인데,
검색 결과는 SQLite에서 조립되므로 고아 엔진 항목은 답을 오염시키지 않고
다음 재구축에서 정리된다. **덜 나쁜 쪽으로 실패하도록 방향을 정한 것**이지
없앤 것이 아니다.

영역이다 — '같은 관련도라면 증류된 노트가 원시 턴보다 앞선다'는 규칙이 필요한데,

### 13.0 먼저 — 잴 도구가 없어졌다

valuein 레포에 쓰지 않는 이유는 그쪽 git에 손대지 않기 때문이고, 이 레포에
두지 않는 이유는 public이기 때문이다.

### 13.1 골드셋이 결론을 미리 정하지 않게 하는 법

첫 시도는 **스스로 반려됐다.** 통합 노트 20건에서 질문(실제 사용자 발화의
패러프레이즈)과 정답 구절을 뽑아 15문항을 만들었더니, 새로 쓴 검증기
`benchmarks/verify_conv_gold.py`가 **구절 30개 중 22개가 증류 레인에만
존재**한다고 보고했다. 그 세트로 재면 "노트를 위로 올린다"는 어떤 변경이든
이긴다. 재는 사람이 답을 미리 적어 둔 것이다.

그렇다고 "양쪽 레인에 다 있는 구절"만 고르면 정반대로 기운다 — 원시 턴이
그 사실을 이미 말하고 있는 경우만 골라내는 것이라, 어떤 변경도 이득이 없게
나온다. 그래서 **한 세트로 재기를 포기하고 두 세트로 나눴다.**

| | 세트 | 무엇을 재나 | 구성 |
|---|---|---|---|
| **A** | `valuein_conv_gold.json` (15문항) | 원시 턴이 **답하는 노트를 밀어내는가** | 정답 구절이 증류 레인에만 있음 (의도된 비대칭) |
| **B** | `valuein_conv_gold_rawonly.json` (10문항) | 강등이 **과하지 않은가** | 정답 구절이 원시 레인에만 있음, 13/13 검증 |

A는 혼자 읽으면 안 된다 — conv 레인을 통째로 지워도 만점이 나온다. B가
그것을 막는다. B는 기계적으로 팠다: conv 청크 400개를 seed 3으로 뽑아
18~46자 문장 중 **conv에 1~3회 등장하고 비-conv에는 0회**인 것만 남긴 뒤,
잡담이 아니라 사실인 것을 골랐다.

### 13.2 진단 — 관련도가 아니라 스플라이스 순서였다

```
_merge_memory_results(..., head_limit=plan.memory_slots)   # 0번 자리에 증류 헤드
_merge_conv_results(...)                                    # 0번 자리에 conv 헤드 ← 나중에 실행
```

conv 스플라이스가 **나중에, 같은 0번 자리에** 끼어든다. 그래서 conv 후보가
하나라도 있으면 **1~3위를 원시 턴이 전부 가져간다.** 관련도 비교의 결과가
아니라 실행 순서의 결과다. 실측(수정 전):

```
Q "지난번에 워크트리 지웠던 얘기 뭐였지"
  1~3위 conv_turn
  4위 memory_card · 5위 qa/consolidated/…-aa0b76e9.md   ← P0가 만든 통합 노트
```

### 13.3 규칙과, 그것을 가중치로 쓰지 않은 이유

> **기억 답변 안의 순서는 도착한 레인이 아니라 증류 단계가 정한다.**
> 통합 노트·카드·qa가 원시 대화 턴보다 앞선다. 노트는 사실을 **진술**하고
> 턴은 그것을 **포함**할 뿐이기 때문이다.

"같은 관련도라면"을 숫자로 쓰지 않았다. 두 레인의 점수는 애초에 비교 가능한
값이 아니고(그래서 둘 다 score merge가 아니라 rank-bounded splice다),
비교 불가능한 것에 교차 가중치를 붙이면 **숫자를 입은 추측**이 된다.
그래서 규칙은 **위치**로 표현했다: conv 헤드를 증류 헤드 **아래**로 내린다.

**예외 하나 — in-flight 턴은 계속 맨 앞이다.** 지금 일어나는 중인 턴은
아직 아무도 증류할 기회가 없었으므로 위 규칙이 할 말이 없다.

### 13.4 상류에서 하나 더 — conv는 슬롯 플래너가 모르는 유일한 레인이었다

`_merge_conv_results`가 `head_limit = min(3, limit)`로 **자기 예산을 스스로
잡고 있었다.** WS1 docstring이 금지한 바로 그 형태다("각 레인이 자기 예산을
계산하고 아무도 합을 비교하지 않는다"). 결과: recall 질의마다 conv가 10칸 중
3칸을 가져가는데 `plan.chunk_floor`는 7이라고 기록했다 — **응답이 지키지 않는
숫자**를 계획이 적고 있었다.

conv 검색을 `plan_slots` **위로** 옮기고 `n_conv`/`conv_slots`를 추가했다.
크기는 그대로(3) 두었다 — 이번 변경은 **장부를 사실과 맞춘 것이지 배분을
바꾼 것이 아니다.** 크기를 줄이려면 대화 축을 재는 신호가 있어야 하는데,
아래에서 보듯 세트 B가 0.00이라 아직 잴 대상이 없다.

unfinished 0.

### 13.6 이 라운드가 새로 드러낸 것

**① 원시 대화 레인은 자기만 아는 사실을 못 꺼낸다.** 세트 B는 전 구간
`answer_found 0.00`이다. conv로 레인을 한정해도 대부분 top-20 안에 안 들어온다.
사실이 1,800자 턴 청크 안의 한 문장이라 청크 전체 임베딩이 턴의 전반적
화제에 지배된다 — **랭킹이 아니라 청킹 입도 문제**다. 백필의 가치는 여기서
막혀 있다. 이번 변경이 아무것도 잃지 않은 이유이기도 하다: 잃을 것이 이미 없었다.

**② 답이 `limit`에 따라 후보 풀에 들어오기도 하고 안 들어오기도 한다.**
C13은 `limit=10`에서 통합 노트가 top-10에 아예 없고 `limit=30`에서 1위다.
`retrieval_depth`가 `limit`에 연동돼 있어서 생기는 일인데, **사용자가 요청한
결과 개수가 무엇을 찾을 수 있는지까지 바꾸는 것은 계약이 아니다.**

**③ `--without` 아블레이션은 천장이 아니다.** 러너가 아블레이션 때
`limit*3`으로 검색하므로 ②와 같은 이유로 유리해진다. 러너 주석에 명시했고,
이번 전/후 비교는 **아블레이션이 아닌 같은 팔**에서만 했다.

**④ 골드셋을 지우면 그 라운드의 주장도 같이 지워진다.** 스크럽이 옳았지만
이관이 빠졌다. 재는 것은 레포 밖 `~/.hybrid-search/benchmarks/`에 두고,
러너와 검증기만 커밋한다.

### 13.7 다음

1. **conv 청킹 입도** — 턴 단위 청크가 문장 단위 사실을 숨긴다. 세트 B가
   0.00인 한 대화 백필의 가치는 측정도 회수도 안 된다. **최우선.**
2. **`retrieval_depth`를 `limit`에서 떼기** — 무엇을 찾을 수 있는지는
   몇 개를 보여줄지와 독립이어야 한다.
3. **conv 헤드 크기 재검토** — 1번이 풀려 세트 B가 움직이기 시작한 뒤에.
   지금 줄이면 측정 없이 줄이는 것이다.
4. **선주입 채택률 재측정** — §11 P1이 예산을 360→2,400자로 늘렸고 이번에

## 14. 라운드 4 — 무엇을 찾을 수 있는가, 그리고 무엇을 회상으로 보는가 (2026-09-08)

§13.7의 1·2를 착수했다. **1번의 진단이 틀렸다는 것부터 적는다.**

### 14.0 정정 — "청킹 입도 문제"가 아니었다

§13.6 ①에 "사실이 1,800자 턴 청크 안의 한 문장이라 청크 전체 임베딩이 화제에
지배된다 — 랭킹이 아니라 청킹 입도 문제"라고 썼다. 근거는 "conv로 레인을
한정해도 top-20에 안 들어온다"였는데, 그 top-20은 **최종 조립 결과**였지
conv 레인 자체의 순위가 아니었다. 레인을 갈라 다시 재니:

| | BM25 순위 | 벡터 순위 |
|---|---|---|
| R4 임베딩 미독 | **1** | 5 |
| R10 자동 선택 | **1** | 200 |
| R2 구분선 문턱 | 108 | **1** |
| R1 그림을 글로 | 8 | 91 |

**목표 청크는 이미 잘 검색되고 있었다.** 청킹은 범인이 아니다. 진짜 원인은
셋이었고, 셋 다 다른 층에 있었다.

### 14.1 원인 ① — 회상형 질문이 회상으로 분류되지 않는다

`_MEMORY_INTENT_KO`는 리터럴 목록이다. 한국어 활용이 그것을 이긴다:
`했지`는 있는데 `했었지`가 없고, `뭐였지`는 있는데 `뭐였더라`가 없고,
`나눴지`·`골라냈지`는 아예 없다. 골드셋에서 **A 15문항 중 9개, B 10문항 중
7개**가 회상형인데 topical로 분류됐다.

그리고 오분류의 대가는 "순위가 나빠짐"이 아니다 — **conv 레인이 아예 돌지
않는다.** 답을 가진 턴이 검색조차 안 된다. §13에서 세트 B가 0.00이었던 진짜
이유가 이것이다.

**규칙**: 종결 어미가 **ㅆ 받침(과거 표지 았/었/였과 그 축약형 했·됐·봤·뒀·
냈·눴…) + 지/더라/던가**면 회상형이다. 문장 끝에 고정하고 구두점을 벗긴
뒤 판정하므로 `했지만` 같은 절은 걸리지 않는다. 있/없/겠은 ㅆ 받침이지만
과거 표지가 아니라 제외한다(`있지`는 회상이 아니고, `있었지`는 앞 음절이
`었`이라 여전히 걸린다).

**`나`는 넣지 않았다.** 상태를 묻는 평범한 의문형(`되나`, `하나`)이라
과거 어간 + 나는 "그게 됐나?"이지 "뭘 정했지?"가 아니다. 넣었더니 rationale
질문(`왜 세워졌나`)이 기억 레인으로 넘어가 10칸 중 6칸을 무관한 기록에
내주고 답 문서가 1위 → 7위로 밀렸다(코드 축 primary-top5 0.92 → 0.88).
빼도 두 conv 세트는 그대로였다.

### 14.2 원인 ② — 몇 개를 보여줄지가 무엇을 찾을 수 있는지를 바꿨다

`retrieval_depth = limit * 3`. `limit=10`이면 후보 풀이 30, `limit=30`이면
90이다. C13의 통합 노트는 30에서는 후보에 없고 90에서 1위였다.
**계약이 아니다** — 표시 개수와 회수 가능성은 독립이어야 한다.

`SearchConfig.retrieval_depth_floor = 100`. `limit * 3`은 바닥을 넘어설
때만 승계한다(limit ≳ 33). 지연은 +2% 수준(원격 임베딩 왕복이 지배적).

### 14.3 원인 ③ — 최우선 기억 단위에 답이 없었다

②·①을 고치고 코드 축을 재니 R5(`왜 세워졌나`)가 1위 → 7위였다. 상위 3건을
열어 보니 **메모리 카드의 본문이 검색 텔레메트리**였다:

```
summary: "- **query_type**: ENGLISH_NL - **bm25_weight**: 0.4
          - **time**: 2099.4 ms - **chunks_searched**: 19618"
decisions: []   followups: []
```

카드 생성기가 답이 들어갈 자리에 그 질의의 계측값을 적었다. 본문 전체가
출처(파일 목록 + "when to use") 뿐이다. **valuein 카드 13개 전부, 이 레포는
16개 중 9개**가 이 형태이고, `memory_card`는 기억 헤드에서 `qa_log`보다
**우선순위가 높다** — 최우선 답변 단위에 답이 없었다.

`quality.card_has_no_answer()`: 텔레메트리 마커 2개 이상 + `decisions: []` +
`followups: []`. 보수적으로 잡았다(결정이 하나라도 기록된 카드는 살린다 —
valuein 13개 중 10개만 걸린다). 이런 카드는 **기억 헤드의 보장 슬롯을 못
가진다.** 일반 청크 스트림에는 남는다 — 파일 목록은 값이 있다.

### 14.4 채택하지 않은 것 — conv 레인 lexical rerank

다른 두 레인은 2차 lexical rerank를 받는데 conv 레인만 없었다. 한 문장짜리
사실이 긴 에피소드 청크에 묻히는 상황에서 term-coverage야말로 살아남는
신호이므로 당연히 이길 줄 알았다. **재보니 아무것도 아니었다**:
세트 A 동일, 세트 B MRR 0.037 → 0.033. 게다가 창을 풀 풀로 넓히면
"깊은 저신호 청크가 coverage만으로 헤드에 올라오지 못한다"는 기존 가드가
사라진다. **아무것도 사지 못하는 변경이 그 값을 치를 수는 없다.** 되돌리고,
왜 안 되는지를 코드 주석으로 남겼다.

한 번은 "창을 넓혔더니 세트 A가 0.73 → 0.80"으로 보였다. 그건 아래의 측정
결함이었다.

### 14.5 측정을 두 번 고쳐야 했다

**① 코퍼스가 재는 동안 움직인다.** valuein 인덱스가 20분 만에 +80 청크
늘었다 — 다른 세션이 일하고 있었다. 같은 코드로 잰 세트 A가 40분 간격으로
top3 0.40 → 0.20이 나왔다. **한 시간 간격의 전/후는 두 랭킹이 아니라 두
코퍼스를 비교한 것이다.** 이번 라운드의 모든 수치는 `~/.hybrid-search`를
통째로 복사한 **얼린 스냅샷**에서 다시 쟀고, 두 러너에 `--config`를 붙여
누구든 같은 방식으로 잴 수 있게 했다.

**② 임베더가 비트 단위로 안정적이지 않다.** 같은 문자열 두 번에 코사인
0.99998, 최대 성분 차 5.8e-4. 얼린 인덱스에서 3회 반복하면 스프레드는
0.00이었지만, 근접 동점에서는 rank ±1을 뒤집을 수 있다. `run_conv_bench.py`에
`--repeat N`을 넣어 mean과 min…max, 그리고 **noise floor**를 같이 찍는다 —
그 아래 델타는 주장하지 않는다.

### 14.6 실측 (얼린 스냅샷 · 3회 반복 · 스프레드 전부 0.00)

| | 기준선(§13 HEAD) | 라운드 4 |
|---|---|---|
| A answer_found | 0.53 | **0.80** |
| A answer_in_top3 | 0.20 | **0.53** |
| A MRR | 0.140 | **0.393** |
| B answer_found | 0.00 | **0.20** |
| B MRR | 0.000 | **0.033** |
| 코드 primary-top5 | 0.92 | 0.92 |
| 코드 recall@10 | 0.77 | 0.77 |
| 코드 memory@3 | 0.16 | 0.16 |
| 코드 read_count | 2.40 | 2.44 |

**기여도 분리** (각 변경을 하나씩 끄고 재측정):

| 끈 것 | A found | A top3 | B found |
|---|---|---|---|
| (전부 적용) | 0.80 | 0.53 | 0.20 |
| depth floor | 0.60 | 0.40 | 0.20 |
| 분류기 | 0.67 | 0.33 | **0.00** |
| conv rerank | 0.80 | 0.53 | 0.20 |

**분류기만이 세트 B를 0에서 꺼낸다.** depth floor는 세트 A의 절반을 가져온다.
conv rerank는 기여가 없어 채택하지 않았다.

테스트 **1,715 통과**(신규 31: 회상 어미 23 · 빈 카드 5 · depth floor 3).

### 14.7 남은 것

1. **세트 B는 아직 0.20이다.** 회상으로 분류되기 시작했을 뿐, 원시 턴이
   가진 사실의 80%는 여전히 못 꺼낸다. 목표 청크가 한 레인에서는 1위인데
   융합 후 3칸짜리 헤드에 못 드는 경우가 남아 있다(R10: BM25 1위, 벡터 200위).
   RRF가 한쪽에서만 뛰어난 후보를 벌하는 문제이고, coverage rerank는 답이
   아니었다(§14.4). **다음 라운드 최우선.**
2. **텔레메트리 카드를 만드는 생성기 자체.** 이번엔 검색 단에서 막았을 뿐
   카드는 계속 그렇게 만들어진다. 상류는 카드 생성 코드다.
3. **`나` 계열 회상 질문**은 여전히 놓친다(`썼었나`). 상태 질문과 구분할
   신호가 어미 하나로는 부족하다.
4. **회상 질의의 슬롯 배분** — memory_intent면 10칸 중 6칸이 기억 레인이고
   코드는 최소 1칸이다. R5에서 보듯 답이 문서에 있는 why 질문에는 과하다.
   세트 A/B가 이제 신호를 내므로 측정하면서 손댈 수 있다.
