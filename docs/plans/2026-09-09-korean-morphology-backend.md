# 한국어 형태소 백엔드 — 하드코딩 목록은 분석기의 대체물이었다

**작성** 2026-09-09 · **상태** 구현·측정 완료 · **선행** `docs/plans/2026-09-09-topic-matcher-audit.md`

---

## §1. 질문

"한국어 불용어를 하드코딩하는 게 맞나. 이런 건 검색하면 나오는 것 아닌가.
다른 연구도 있을 것 같고, 영어 불용어도 마찬가지고."

앞 작업(`78090a5`)에서 한국어 접두 불용어 97개를 손으로 넣었다. 정당한 의심이라
조사했다. **결론부터: 영어는 이미 표준을 따르고 있었고, 한국어는 표준이 없으며,
진짜 표준 기법은 목록이 아니라 형태소 분석이었다.**

---

## §2. 영어 — 이미 표준의 부분집합이었다

| | 개수 | 외부(`stopwordsiso` en) 교집합 |
|---|---|---|
| `_EN_STOPWORDS` | 100 | **99** |
| `_EN_GENERIC_WORDS` (0.3배) | 81 | 27 |

불용어 100개 중 우리 것만 있는 건 `explain` 하나다(Q&A 문두 표현). 즉 이쪽은
하드코딩처럼 보이지만 실질적으로 표준 목록이다.

**저정보 목록은 다르다.** 81개 중 **54개는 어떤 표준 불용어 목록에도 없다** —
csv, json, pdf, utf, euc, fixture, api, client, server, mb, kb, kst. 이건
"개발 Q&A 코퍼스에서 정보량이 낮다"는 **도메인 판단**이고, 어떤 언어학 자료도
공급하지 않는다. 여기는 손으로 쓰는 게 맞고, 앞으로도 그렇다.

## §3. 한국어 — 표준이 없고, 있는 것도 못 쓴다

- 문헌상 **절대적 표준이 없다.** 국립국어원 말뭉치에서 고빈도 형태소를 뽑아
  293개를 고른 연구가 있으나 표준은 아니고, 실무 표준은 "KoNLPy로 형태소 분석
  후 조사·어미 제거"다.
- `stopwordsiso` 한국어 595개를 그대로 쓰면 **이 프로젝트가 의존하는 주제어가
  죽는다** — 근거, 결론, 기준, 비교, 시간, 시작, 아이디어. 범용 텍스트마이닝용이라
  목적이 다르다. 2글자 접두 충돌(그래프·그리드·아이디어)도 그대로다.
- 우리 목록 97개 중 외부가 뒷받침하는 건 **40%뿐**이고, 나머지 58개는 전부
  **활용형**(있습/했다/됩니/합니)과 **조사 붙은 의존명사**(것이/것은/것을)다.

**여기가 핵심이다.** 외부 목록이 활용형을 안 갖는 이유는 그것들이 전부
**형태소 분석기를 앞단에 가정**하기 때문이다. 우리 매처엔 분석기가 없고,
2글자 접두가 그 대체물이다. **그러니 손목록은 연구의 대체물이 아니라
분석기의 대체물이었다.** 질문이 옳았다.

## §4. 형태소 분석이 구조적으로 해결하는 것

`kiwipiepy`를 붙이자 태그가 대부분을 처리한다:

```
그것 NP · 실제로 MAG · 다른 MM · 것 NNB · 하 VV+었 EP+습니다 EF   ← 전부 태그로 제거
이미지 NNG · 그래프 NNG · 그리드 NNP · 정산 NNG · 근거 NNG        ← 주제어 보존
이미 MAG                                                      ← 접두 충돌 소멸
```

- 조사(J\*)·어미(E\*)·접사(X\*)·의존명사(NNB)·대명사(NP)·수사(NR)·관형사(MM)·
  부사(MAG/MAJ)가 태그로 걸러지고, 이다/아니다는 VCP/VCN으로 자기 태그를 갖는다.
- **2글자 절단이 사라지므로 충돌 문제 자체가 없어진다.**
- 남는 손목록은 **경량용언 + 형식명사 20여 개**뿐이다(하/되/있/없/같/위하/대하/
  통하 …, 경우/정도/자체/나머지). POS만으로는 못 거르는 것들이다.

**계측이 내 실수를 하나 잡았다.** 초안에서 `이유`를 형식명사로 넣었더니 코퍼스
문서빈도가 0%로 떨어졌다. 이 프로젝트의 논지가 "why를 답하는 메모리"인데
`이유`를 버리고 있었다. 뺐고, 코드에 왜 없는지 적어 뒀다.

## §5. 비용 — 그래서 선택 의존성이다

| | 값 |
|---|---|
| 모델 다운로드 | **104MB** (`kiwipiepy_model`) |
| 상주 메모리 | RSS +약 600MB |
| 색인 처리량 | 0.35M자/s (qa 2,000건 ≈ 15초) |
| 질의 시점 | 문서당 **2.1ms** (접두 0.2ms, 9배) → 후보 30건이면 질의당 +64ms |
| 최초 로드 | 485ms 1회 |
| Python 3.14 ARM 휠 | 정상 |

질의 비용은 감당 가능하다(검색 자체가 300~600ms). **104MB와 RSS가 문제다.**
`pip install` 한 방을 내세우는 패키지라 기본 의존성으로는 못 넣는다.

```
pip install memory-layer-mcp            # 지금과 동일. 접두 백엔드
pip install memory-layer-mcp[korean]    # 형태소 백엔드
```

없으면 `snowballstemmer` 폴백과 같은 모양으로 접두 경로로 내려간다.

## §6. 두 백엔드는 토큰이 호환되지 않는다 — 표식을 박았다

extra를 설치하거나 지우면 **qa 파일 하나 건드리지 않고 토큰화가 바뀐다.**
mtime도 내용 해시도 이걸 못 본다. 그런데 supersession 매핑은 인덱스 시점에
저장된다 — 오늘 아침에 내가 직접 밟은 함정이다.

그래서 `replace_qa_supersession`이 `index_meta`에 백엔드를 찍고,
질의 경로는 다른 백엔드가 만든 매핑을 **읽지 않는다**(경고 후 무시 —
틀린 정정은 없는 것보다 나쁘다). `status`가 그 상태를 한 줄로 보여준다:

```
⚠ qa supersession was built by ko-prefix-1, running ko-kiwi-1 — ignored until `reindex`
```

## §7. 임계값은 백엔드별이어야 했다 — 그리고 골드셋만으로는 못 정한다

분석기는 접두 경로가 남기던 조사·활용형을 버린다. 그러면 **비율의 분모와 분자가
같이 줄어 모든 겹침이 올라간다.** 진짜 같은 쌍이 0.57 → 0.85로 오르는 건 좋은데,
어휘만 공유하는 쌍도 같이 오른다.

접두 임계값을 형태소에 그대로 쓰면:

- 골드셋 88쌍: 36/37, 오탐 1 → **FAIL**
- 그 전에 dev-workflow 계층까지 넣었던 판에서는 골드셋 **전 슬라이스 PASS**인데
  코퍼스 수용률이 **10.6 → 14.5로 상승**했다. 늘어난 쌍은 눈으로 보면 쓰레기다.

**골드셋 88쌍만으로는 이걸 못 본다.** 오늘 두 번째다(첫 번째는 209건의 잘못된
대체가 사라졌는데 20문항이 하나도 안 움직인 것). 그래서 보정 도구를 새로 만들었다
— `benchmarks/topic_threshold_sweep.py`:

- **골드셋 = 재현율 바닥** (adjacent/bridge 오탐 0, 언어별 same 하한)
- **실제 코퍼스 = 정밀도 신호** (무작위 쌍 수용률 최소화)
- 쌍별 겹침을 한 번만 계산해 캐시하므로 전 격자를 초 단위로 훑는다.

3번째 임계값 `_ANSWER_ONLY_OVERLAP`도 이제 스윕에 들어간다. 교차언어·명령형 쌍은
질문 토큰을 하나도 공유하지 않아 답변 전용 경로로 가는데, 기존 스윕은 이 축을
아예 안 훑고 있었다.

## §8. 답변 없는 레코드 — 질문을 쫓다 나온 진짜 구멍

형태소 백엔드가 Set B 한 문항(B35)을 잃길래 원인을 팠더니, 한국어와 아무 상관
없는 것이 나왔다.

B35의 정답 청크가 **셸 명령 붙여넣기 턴에 의해 supersession으로 덮어써지고
있었다.** splice는 정원이 찼을 때 낡은 히트를 **교체**하므로, 답이 결과에서
통째로 사라졌다. 두 질문이 공유한 것은 **프로젝트 자기 이름의 조각 두 개**뿐이었다. 셸 프롬프트에도, 워크트리 경로에도 박혀 있으니 자기 코퍼스
안에서 이보다 정보량 낮은 토큰이 없다.

어떻게 통과했나. 한쪽에 `## Answer excerpt`가 없으면 `same_topic`은
**질문 겹침 하나로**(`_QUERY_ONLY_OVERLAP` = 0.6) 판정한다. 질의 시점에는
질의 자체가 후보를 걸러 놓아서 괜찮지만, **코퍼스 전체에서는 프로젝트 이름만
공유해도 넘는다.**

규모:

| | |
|---|---|
| 답변 excerpt 없는 qa 레코드 | 305 / 2,017 (**15%**) |
| 그것이 낀 supersession 매핑 | 179 / 396 (**45%**) |

**이건 이번 매처 작업이 만든 게 아니다.** 그 전부터 있었고, 픽스처에 전부 답변이
있는 골드셋으로는 영원히 안 보인다.

**첫 수정은 틀렸다.** "양쪽 다 답변이 있어야 한다"로 막았더니 Set B는 돌아왔는데
Set A가 0.70 → 0.65로 떨어졌다. **답변 없는 원시 턴이 그것으로 만든 통합 노트에
의해 대체되는 건 설계된 노출 경로**였고(그게 노트가 원시 턴을 친 사람에게
닿는 방법이다), 그걸 같이 막은 것이다.

고친 규칙 두 개:

1. **이기는 쪽은 반드시 답이 있어야 한다.** 답 없는 레코드는 무엇도 정정할
   수단이 없고, 교체하면 진짜 답이 빈 것으로 바뀐다.
2. **한쪽에 답이 없으면 질문이 거의 같아야 한다** (`_ANSWERLESS_QUERY_OVERLAP`
   = 0.85). 이 코퍼스에서 0.6을 넘는 답변 없는 쌍의 질문 겹침 중앙값이 0.91이라,
   정당한 쌍은 살아남고 "같은 프로젝트일 뿐"인 쌍은 걸러진다.

## §9. 측정

기준선 = 오늘 아침 커밋 `78090a5` (접두 백엔드 + 손목록).

| | 기준선 | **기본 설치** (접두 + §8) | 형태소 extra |
|---|---|---|---|
| 골드셋 게이트 | PASS 35/37 | PASS 35/37 | PASS 35/37 |
| **술어 수용률** | 10.6 / 10k | **9.7** | **5.7** |
| Set A found / **top3** / MRR | 0.75 / **0.70** / 0.571 | 0.75 / **0.70** / 0.571 | 0.75 / **0.70** / 0.571 |
| Set B found | 0.02 | **0.05** | 0.02 |
| 코드축 top5 / recall / memory@3 | 0.92 / 0.77 / 0.16 | 동일 | 동일 |
| 테스트 | 1,740 | 1,748 | 1,748 |

세션 시작 시점(오늘 아침 작업 전)의 술어 수용률이 19.2였으니,
**기본 설치 기준 19.2 → 9.7 (−50%), extra 기준 19.2 → 5.7 (−70%)**다.

**읽는 법:**

- **§8은 기본 설치가 그냥 이긴다.** Set B가 0.02 → 0.05로 올랐고 나머지는
  전부 그대로다. 한국어 질문을 쫓다 나왔지만 한국어와 무관하다.
- **형태소 extra는 트레이드다.** 묶음 정밀도는 46% 더 좋은데(9.7 → 5.7),
  이 코퍼스에서는 Set B 문항 2개를 기본 설치보다 덜 찾는다. 더 엄격해서다.
  → **권고: 기본이 전반적으로 더 낫다. extra는 잘못된 정정을 최대한 줄이고
  싶을 때(그리고 104MB가 괜찮을 때) 켠다.**

### 9.1 채택하지 않은 갈래

**dev-workflow 저정보 계층**(머지/푸시/배포/커밋/브랜치를 0.3으로). 수용률을
8.5 → 5.9까지 끌어내렸고 골드셋도 통과했는데 **Set A top3가 0.70 → 0.65로
떨어졌다.** 무너진 건 정확히 한 질의 — "메인에 올리기 전에 뭘 확인하기로
했었지" — 즉 **절차 자체를 묻는 질문**이다. git 어휘를 저정보로 내리면 git
절차를 묻는 사람이 답을 잃는다. `TestDevWorkflowVocabularyStaysDistinctive`가
이 판단을 박아 둔다.

**1글자 어간을 버리던 규칙.** `len < 2`는 2글자 접두용인데 어간에도 걸려 있어
`얇다 → 얇`, `값`, `물`이 조용히 사라지고 있었다. 형태소 경로에서 풀었다.

## §10. 남은 것

1. **경로 보일러플레이트는 처리했다** — 파일 경로를 basename으로 줄이는
   `strip_path_directories`를 넣었다(첨부 배너 제거 옆). 디렉토리 체인은 레포
   안의 모든 턴이 공유하는 비계인데 snake_case라 식별자 3배 가중치를 받고 있었다.
   파일 **이름**은 주제이므로 남긴다.
2. **Reflector 클러스터링.** 같은 엄격 술어를 쓰므로 이번 변경으로 묶음이
   더 좁아진다. 수동 트리거라 미측정.
3. **코퍼스 신호는 코퍼스별이다.** 스윕을 다른 프로젝트(n=239)에 돌리면 다른
   최적점이 나온다. 배포되는 값은 큰 코퍼스(n=1,981)에서 고르고 골드셋으로
   교차검증했다. 사용자 코퍼스마다 재보정하는 길은 열어 뒀지만(도구가 있다),
   기본값은 하나여야 한다.
4. **프로젝트 자기 이름.** §8의 쌍을 이어 준 것은 결국 프로젝트 이름이었다.
   자기 코퍼스에서 가장 정보량 낮은 토큰인데, 사용자마다 다르니 하드코딩할 수
   없다. 인덱스 시점에는 `pinfo.name`으로 알 수 있으므로, 매처에 프로젝트
   컨텍스트를 주는 길이 열려 있다. 지금은 §8의 두 규칙이 증상을 막고 있다.
5. **IDF로 목록을 대체하는 길은 막혀 있다.** 문서빈도로 계층을 자동 도출하면
   골드셋으로 검증할 수 없다 — 88쌍에는 코퍼스가 없어서 DF를 계산할 수 없다.
   코퍼스 적응형으로 가려면 골드셋에 동반 DF 표를 붙여야 하고, 임계값도 다시
   스윕해야 한다. 지금은 하지 않는다.
