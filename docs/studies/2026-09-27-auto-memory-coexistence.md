# Claude Code auto memory 와의 공존 — 이중 주입 실측 (2026-09-27)

**질문** (계획 `2026-09-27-open-the-doors.md` §3 0-3): 우리 SessionStart · UserPromptSubmit 주입과
Claude Code auto memory 가 같은 내용을 두 번 넣는가? 넣는다면 얼마나?

## 1. 두 채널이 실제로 넣는 것 (이 레포 트랜스크립트 14개에서 확인)

| 채널 | 언제 | 무엇 |
|---|---|---|
| auto memory | 세션 시작, 시스템 프롬프트 | `MEMORY.md` 인덱스(첫 200줄/25KB). 토픽 파일은 모델이 필요할 때 **Read** 로 연다 — 자동 첨부 레코드는 트랜스크립트에 없다 |
| 우리 SessionStart | 세션 시작 | 최근 Q&A 요약 몇 줄 · selfeval 한 줄 · (주기 측정 안내) |
| 우리 UserPromptSubmit | 탐색형 프롬프트마다 | pre-fetch 상위 히트(≤6, ≤2,400자) — 코드 위치 · 인용된 qa/대화/커밋 |

2026-08-31 플랫폼 조사(공식 문서 확인)의 사실: auto memory 에는 과거 대화 검색이 없고, 트랜스크립트는
`cleanupPeriodDays` 뒤 지워진다(메모리 디렉터리만 남는다).

## 2. 사전 등록 (측정 전)

- **대상**: 이 레포의 Claude 트랜스크립트 전부. 우리 주입은 `hook_additional_context` 첨부에서 읽는다.
- **auto memory 코퍼스**: `MEMORY.md` + 토픽 파일. 턴마다 **그 턴 시각 이전에 만들어진 파일만** 쓴다
  (파일 생성 시각 기준 — 나중에 쓴 메모리를 과거 주입과 겹친다고 세지 않기 위해). 내용은 현재 판본이다(한계).
- **겹침 판정**: pre-fetch 히트 하나(또는 SessionStart 주입 하나)가 그 턴에 유효한 메모리 파일 하나와
  고유 id 1개 이상 또는 3어절 문구 2개 이상을 공유 — selfeval v1.2 인용 채택과 같은 규칙
  (`selfeval_evidence.quoted_adopted`), 배제 텍스트는 사용자 프롬프트.
- **보고**: (1) 크기 — 세션당 MEMORY.md 글자 수, SessionStart 주입 글자 수 중앙값, 턴당 pre-fetch 글자 수 중앙값.
  (2) 겹침 — pre-fetch 주입 중 겹치는 히트가 1개 이상인 비율, 히트 단위 비율, 히트 종류별(코드 · qa · 대화 · 커밋).
  (3) SessionStart 겹침 비율. (4) 겹침이 많은 메모리 파일 상위 5(파일명만). (5) 정밀도 표본 — 겹침으로
  판정된 히트 최대 10건을 판정자가 읽고 "같은 사실을 두 번 넣었나"를 예/아니오.
- **예측**: 겹침은 0 보다 크다. pre-fetch 히트의 **다수는 겹치지 않는다**(메모리는 큐레이션된 결론이고
  pre-fetch 는 코드 위치와 원시 턴이다). 겹침은 qa · 대화 히트에 몰리고 코드 히트에는 거의 없다.
- **판정 기준**: 히트 단위 겹침이 20% 이상이거나 겹침의 정밀도가 과반이면서 비율이 10% 이상이면 "충돌이
  실재" 로 보고 해법을 **제안만** 한다(주인 판단). 그 밖이면 README 에 공존 방식만 적는다.
- 측정 중 src 수정 없음. 출력은 레포 밖. 메모리 본문·주입 원문은 이 문서에 인용하지 않는다.

## 3. 결과 (2026-09-27)

대상: 트랜스크립트 14개, SessionStart 주입 15건, pre-fetch 주입 416건(히트 2,240개). 메모리 파일 44개.
과거 pre-fetch 중 26건은 당시 임베딩 장애로 BM25 전용(degraded)이었다 — 이미 주입된 기록을 세는 것이라
제외하지 않았다(주입된 글자가 곧 측정 대상이다). 행 단위 결과는 레포 밖에만 있다.

### 3.1 크기

| 채널 | 단위 | 글자 수 |
|---|---|---|
| auto memory `MEMORY.md` | 세션당 1회(고정) | 6,025 |
| 우리 SessionStart | 세션당 1회, 중앙값 | 360 |
| 우리 pre-fetch | 탐색형 프롬프트당, 중앙값 | 1,890 |

pre-fetch 는 세션당 평균 약 28회라, 주입량으로는 우리 채널이 auto memory 인덱스보다 한 자릿수 크다. 다만
auto memory 는 **모든** 세션에 고정으로 들어가고, pre-fetch 는 탐색형 프롬프트에만 들어간다.

### 3.2 겹침 (등록한 규칙 그대로)

| | 전체 | 겹침 | 비율 |
|---|---|---|---|
| pre-fetch 주입(겹치는 히트 ≥1) | 416 | 386 | 0.93 |
| 히트 | 2,240 | 1,406 | 0.63 |
| — 코드 히트 | 1,419 | 956 | 0.67 |
| — qa 히트 | 448 | 173 | 0.39 |
| — 커밋 히트 | 237 | 207 | 0.87 |
| — 카드 · 대화 · 기타 | 136 | 70 | 0.51 |
| SessionStart 주입 | 15 | 15 | 1.00 |

겹침이 많은 메모리 파일 상위 5: `project_conversation_indexer_revival.md` 673 · `MEMORY.md` 636 ·
`project_bf16_simsimd_crash.md` 528 · `project_answerless_gate.md` 386 · `feedback_no_new_mcp_tools.md` 370.
임베딩 크래시 메모가 3위라는 것부터가, 겹침이 사실이 아니라 공통 식별자를 세고 있다는 신호다.

### 3.3 정밀도 표본 (로컬 판정)

| 표본 | 같은 사실을 두 번 넣음 | 같은 주제의 다른 사실 | 아님 |
|---|---|---|---|
| 겹침 히트, 중복 제거 후 균등 무작위 10 (276개 중) | 0 | 2 | 8 |
| (참고) 첫 추출 — 파일 앞쪽에 치우친 10 | 2 | 0 | 8 |

겹침 판정은 대부분 **날짜 · 문서 경로 · 흔한 식별자 하나**(`task_state`, `hooks`, `benchmarks`,
`mcp__hybrid-search__hybrid_search`)로 성립했다. 코드 히트 67% · SessionStart 100% 가 그 증거다 — 코드 위치나
"검색 도구를 쓰라"는 안내문이 큐레이션된 사실과 같을 수는 없다. 실제 이중 주입 사례는 "외부 심사 API 키의 위치",
"질문 기반 판정으로 바꾼 결정"처럼 **한 번의 결정이 메모리 파일 · qa 로그 · 커밋 세 곳에 따로 남은 경우**였다.

### 3.4 판정

- **등록 기준의 첫 조항(히트 겹침 ≥ 20%)은 문자 그대로는 발동한다(0.63).** 그러나 이 조항은 정밀도를 조건으로
  두지 않은 설계 결함이었다 — selfeval 의 답↔발췌 규칙을 메모리↔히트에 옮기자 코퍼스 전반의 공통 식별자가 id 로
  잡혔다. 둘째 조항(정밀도 과반)은 성립하지 않는다(0~2/10).
- 예측 대조: "겹침 > 0" 은 맞았다. "히트의 다수는 겹치지 않는다"와 "코드 히트엔 거의 없다"는 **등록 규칙의
  수치로는 틀렸다**(0.63 · 0.67). 정밀도 표본으로 보면 사실상 맞는 방향이지만, 그건 등록한 판정 방식이 아니다.
- 정밀도로 보정한 실제 이중 주입은 **히트의 약 13% 이하**(0.63 × 0.2, 상한)로 추정한다. 표본이 작아 하한은 0 이다.
- 등록 규칙을 따라 **해법은 제안만 한다**(§4). 규칙 개정은 하지 않았다 — 다시 잰다면 id 최소 길이 · 흔한 식별자
  제외 · 문구 전용 기준으로 새로 등록한다.

## 4. 제안 (주인 판단)

두 채널은 **하는 일이 다르다**. auto memory 는 에이전트가 고른 소수의 규칙 · 결정을 **매 세션 고정으로** 싣는다.
우리는 질문마다 코드 · 커밋 · 과거 대화에서 **근거를 찾아** 싣고, 트랜스크립트가 지워진 뒤에도 검색된다.
실측된 이중 주입은 "같은 결정이 세 저장소에 따로 남는" 구조에서 오며, 양이 작고 판별도 어렵다.

| 안 | 내용 | 비용 · 위험 | 권고 |
|---|---|---|---|
| **A. 문서화만** | README 에 공존 방식 · 역할 분담을 적는다. 둘 다 켜 두는 것이 기본 | 0 | **지금 (이 PR)** |
| B. pre-fetch 중복 억제 | 그 세션의 `MEMORY.md` 에 이미 있는 사실을 담은 인용 히트를 뺀다 | 판별기 정밀도가 낮아(§3.3) 오히려 근거 히트를 지울 위험 · 새 기능 | 보류 — 정밀한 판별기가 먼저 |
| C. 메모리 디렉터리 읽기 전용 색인 | auto memory 토픽 파일을 기억 레인 소스로 검색 가능하게 (지금은 모델이 필요할 때만 Read) | 새 기능 · 레포 밖 경로 색인 · 개인 메모 노출 범위 | 보류 — 런칭 뒤, valuein 놓친 사례가 요구하면 |
| D. SessionStart 축소 | 우리 SessionStart 요약을 줄인다 | 겹침이 노이즈였으므로 근거 없음 | 하지 않음 |

A 를 권한다. B · C 는 "문 열기 전 새 기능 금지"(계획 §9)에도 걸린다.
