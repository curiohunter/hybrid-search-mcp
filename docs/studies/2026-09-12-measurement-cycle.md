# 측정 순환 — 사람이 없어도 도는 부분과, 사람만 할 수 있는 부분

**설계·구현** 2026-09-12 · **계기** "남의 컴퓨터에서 재자"는 배포 얘기였고, 요청은
**우리 프로젝트 안에서 도는 순환**이었다.

---

## 무엇이 문제였나

이 레포의 모든 숫자는 지금까지 **사람이 다섯 개 스크립트를 올바른 순서로**,
**스냅샷 뜨는 걸 잊지 않고** 돌려서 나왔다. 그게 두 번 값을 치렀다 —
측정 중에 라이브 인덱스가 움직였고, 반쯤 재빌드된 벡터에 벤치를 돌렸다.

그리고 더 큰 문제: **그 사람이 없으면 아무것도 안 재진다.**

## 순환의 세 조각

```
   사용 ──────────────► qa 레코드가 쌓인다 (실측 주당 ~380건)
                              │
                              ▼
   [1] benchmarks/cycle.py ── 얼린다 · 전 축을 잰다 · 지난 주기와 비교한다
                              │        Set A / Set B / 코드축 / 밀어냄
                              ▼
   [2] benchmarks/judge_displacements.py ── 새 밀어냄을 검증된 판정자에게
                              │
                              ▼
   [3] SessionStart 훅 ─────► 다음 세션이 결과를 본다 (묻지 않아도)
                              │
                              └──► 회귀가 있으면 그게 다음 작업이다
```

### [1] `benchmarks/cycle.py`

기존 러너들을 **측정 규약이 이미 지정한 순서대로** 실행한다. 새 측정은 없다.
스냅샷을 뜨고, supersession을 재계산하고, 세 축과 밀어냄 감사를 돌리고,
`~/.hybrid-search/benchmarks/cycle/<날짜>.json`에 적고, 이전 기록과 diff를 낸다.
게이트가 회귀하면 **exit 1** — 스케줄러에 걸 수 있다.

게이트는 **고정 목표가 아니라 이전 주기 대비**다. 그래야 바가 시스템과 함께
올라가고, 세션마다 "목표를 몇으로 할까"를 다시 논쟁하지 않는다.

`--repeat` 스프레드가 0이 아니면 **회귀가 아니라 오염**이라고 보고한다.
이 라인이 한 번 0.05의 잡음을 회귀로 읽고 쫓아간 적이 있다.

### [2] 그리고 진짜 새로운 것 — **홀드아웃이 매주 다시 찬다**

각 주기가 자기 날짜를 기록한다. **다음 주기는 `--since <그 날짜>`로 감사한다** —
그 규칙이 얼려질 때 **존재하지도 않았던** 레코드로만 채점한다는 뜻이다.

코퍼스 하나와 사용자 한 명이 여럿이 될 수는 없다. 하지만
**임계값을 맞춘 그 레코드들을 더 많이 다시 읽는 것보다, 스스로 다시 차는 테스트
셋이 낫다.** 도그푸드 코퍼스는 주당 ~380건을 만든다 — 4주면 깨끗한 천 건이다.

이건 "학습 데이터에서 측정했다"는 외부 심사의 지적을 **사람 축이 아니라 시간 축**
으로 뚫는다. 완전한 답은 아니지만 공짜다.

### [2-b] 누가 [1]을 돌리나 — 스케줄러가 아니라 에이전트다

크론·launchd에 걸지 않기로 했다. 측정은 수천 번의 검색이고, 사용자가 일하는 시간에
돌면 **같은 임베딩 백엔드를 두고 그 사람의 검색과 다툰다** — 이 세션에서 실제로
벌크 재임베딩 중에 pre-fetch가 BM25 전용으로 떨어지는 걸 봤다. 그리고 이 노트북이
켜져 있는 시간이 곧 사용자가 일하는 시간이다.

**대신 SessionStart 훅이 에이전트에게 지시한다.** 마지막 측정이 7일을 넘으면:

```
[cycle 2026-09-05] 마지막 측정 8일 전
  → 이 세션에 여유가 생기면 `python benchmarks/cycle.py` 를 돌리고 결과를 보고할 것
```

에이전트는 세션이 언제 한가한지 안다 — 긴 작업 사이, 사용자가 답을 읽는 동안,
세션 끝. 크론은 모른다. 그래서 **타이밍 판단을 아는 쪽에 맡긴다.**
규칙은 `CLAUDE.md`에도 박아 뒀다(훅 줄을 놓쳐도 남게).

### [3] `benchmarks/judge_displacements.py`

새로 뜬 밀어냄을 판정자에게 보내 라벨 파일에 `judge: llm`로 적는다.
**사람 라벨은 절대 덮어쓰지 않는다** — 사람 판정이 항상 모델보다 위고, 파일에
둘 다 남아 일치율을 계속 계산할 수 있다.

이게 정당해진 건 **기준이 결정 가능해졌기 때문**이다. 주인의 결정을 규칙에 적은
뒤 같은 31 사례에서 κ가 0.50 → 0.80이 됐다. 그 전이라면 이 단계는 쓰레기를
쌓았을 것이다.

### [4] SessionStart 한 줄

```
[cycle 2026-09-12] Set A top3 0.70→0.65 · 판정 대기 14건
```

**결과를 물어봐야 나오는 루프는 스크립트다.** 이 한 줄이 루프를 닫는다.
깨끗하면 침묵하고, 2주가 지나면 다시 돌리라고 말한다.

## 이 순환이 **못** 하는 것 (그리고 안 하기로 한 것)

- **다른 사람에게도 통하는지는 모른다.** 규칙들이 한 사람의 말버릇에 맞춰져 있다 —
  한국어 가중치, "반복 운영 요청" 조항, `feat/`·`ws-`를 가정하는 실물 정규식.
  밸류인을 아무리 오래 써도 이건 안 흔들린다.
- **사람 채점자는 늘어나지 않는다.** 늘리려 하지 않기로 했다. 이 도구를 쓰는 사람은
  수학학원 원장이고, 채점에 시간을 쓰는 건 이 프로젝트가 존재하는 이유와 어긋난다.

그래서 **판정이 필요한 지표를 헤드라인에서 내린다.** "밀어냄 정밀도 N%"는 진단으로
쓰고, 채택 판정은 **채점자가 필요 없는 네 줄**로 한다:

| 지표 | 사람 필요? |
|---|---|
| Set A / Set B (정답 구절이 고정돼 있다) | 아니오 |
| 코드축 | 아니오 |
| 테스트 1,780여 건 | 아니오 |
| 엣지 수·자기회수 같은 기계적 사실 | 아니오 |
| 밀어냄 정밀도 | **예** ← 진단으로만 |

**사람의 몫으로 남는 것은 하나다** — 쓰다가 짜증 났을 때 한 줄.
그건 selfeval의 행동 신호(배신율·채택률)가 이미 매 턴 자동으로 재고 있고,
사람이 직접 말해 주는 것이 그 위에 얹힌다.

## 부록 — 순환을 처음 돌리자마자 나온 것: 워크트리에는 기억이 없었다

이 순환의 목적은 "밸류인에서 계속 쌓이는 것을 분석해 이 프로젝트를 고친다"였다.
그 관점으로 코퍼스를 처음 훑자마자 나왔다.

**밸류인은 워크트리를 판다. 이 레포는 메인에서만 작업한다.** 그래서 이 레포에서만
개발하면 절대 안 보이는 결함이 있었다.

| | qa 레코드 | 코드 청크 |
|---|---|---|
| `valuein_homepage` (메인) | **2,023** | 10,176 |
| 워크트리 22개 | **전부 0** | 2 ~ 346 |

워크트리는 **각각 별도 프로젝트로 등록**되고, 각자 자기 `.hybrid-search/`를 갖는다.
같은 질문을 같은 레포에서, 폴더만 바꿔 던진 결과:

```
메인 폴더에서   → qa_log 6 · conv_turn 3 · memory_card 1   (메모리 10건)
워크트리에서    → commit 5 · rationale 3 · section 1        (메모리  0건)
```

**원장님이 실제로 일하는 환경에서 메모리 레이어가 사실상 꺼져 있었다.**

### 원인 — 쓰기와 읽기가 서로 다른 방식으로 프로젝트를 골랐다

`hook_runtime.resolve_project_root`는 **2026-09-04에 이미** 링크된 워크트리를
메인 체크아웃으로 되돌리도록 고쳐졌다(그 docstring이 "워크트리 세션은 기억을 하나도
안 남겼다"라고 적고 있다). 그래서 **쓰기는 메인에 정확히 쌓였다.**

그런데 검색은 `orchestrator._detect_primary_project`를 쓰고, 그건 **경로 포함 관계만**
본다. 워크트리 cwd는 워크트리 자신의 등록 프로젝트에 걸리고, 그 인덱스에는 기억이
한 건도 없다. **한 곳에 쓰고 다른 곳에서 찾고 있었다.**

### 수정

두 경로가 같은 함수를 쓰게 했다 — `hook_runtime.canonical_project_root`.
"어느 프로젝트인가"를 정하는 모든 경로는 여기를 지난다.

수정 후 같은 워크트리에서 **메모리 0건 → 10건**, 메인과 결과가 동일하다.
세 축은 무변동(프로젝트 해석만 바뀌고 랭킹은 안 건드렸다).

### 이 사건이 말하는 것

**도그푸드 코퍼스가 하나여도, 그 코퍼스의 *환경*이 다르면 다른 결함이 나온다.**
이 레포(메인 온리)에서만 개발했으면 22개 워크트리 × 0 qa 는 영원히 안 보였다.
그래서 순환은 밸류인을 1차 코퍼스로 삼는 게 맞다 — 거기가 실제 개발 환경이다.

> **주의사항 (신규)**: "어느 프로젝트인가"를 두 곳에서 따로 정하지 말 것.
> 쓰기가 A로 가고 읽기가 B를 보면, 두 경로 각각은 테스트를 통과하면서 시스템은
> 조용히 아무것도 기억하지 못한다.

### 뒤처리 — 유령 22개, 143MB

경로가 사라진 등록 프로젝트가 23개였다(워크트리 21 + 기타 2). 기억(qa/conv/card)을
가진 것은 `proj` 하나뿐이라 그것만 남기고 22개를 지웠다.
**인덱스 480MB → 337MB.** 등록 프로젝트 33개 → 11개.

그리고 다시 안 쌓이게 **정체성 판정을 한 곳으로 모았다.** `canonical_project_root`가
`memory/hook_runtime`에서 **`project.py`로 옮겨졌고**(프로젝트 정체성이 사는 자리다),
이제 네 경로가 전부 그것을 쓴다:

| 경로 | 이전 | 지금 |
|---|---|---|
| Stop 훅 (쓰기) | 워크트리 인식 ✓ | 〃 |
| git post-commit | 워크트리 인식 ✓ | 〃 |
| **검색 (읽기)** | **경로 포함만** ✗ | 워크트리 인식 |
| **인덱싱 (등록)** | **주어진 경로 그대로** ✗ | 워크트리 인식 |

넷 중 둘만 맞았던 것이 유령의 원인이었다. 워크트리에서 `index`를 한 번 돌리면
다시 생겼을 것이다.
